# Criterion 5 — model catalog refresh

Audited 2026-10-14. **Read, not tested.** The gap is real and specific.

## What exists

The catalog is a **generated file**, not a live feed:

- `crates/epsilon-llm/src/catalog/catalog_data.rs` — "GENERATED FILE - do not edit by
  hand. Regenerated by `scripts/regen_catalog.py` from https://models.dev/api.json
  **on 2026-09-21**".
- `scripts/regen_catalog.py` — the generator; fetches models.dev, applies selection
  rules and price mapping. Run manually by a developer, then `cargo fmt` and
  `cargo test -p epsilon-llm`.
- `catalog_is_current_generation` (`catalog.rs:1227`) — a **pin test**: it asserts the
  data is the committed generation, with the row count and provider count recorded in
  the doc comment. Its job is to fail loudly when data and the script drift apart, so
  it is a consistency guard, not a freshness one.
- M20 (`docs/history.md:43`) records "live fetch fixed and auto-firing on picker open" —
  so a live fetch exists somewhere. **Not verified this session.**

## The gap against criterion 5

| criterion 5 asks | state |
|---|---|
| periodic refresh | none — refresh happens when a developer runs a script |
| new / deprecated / capability / context / effort changes tracked | tracked at regen time only |
| provider failure preserves last known good | **structurally true** — the file is committed, so a failed fetch cannot corrupt it. This is the strongest part of the design. |
| manual refresh trigger | a developer script; not a user-facing command |
| indicator of last successful update | **exists but is invisible** — the date is in the generated header and nowhere else |

So the last two rows are the actionable gap, and the first four are satisfied by
construction (offline-first, fail-safe) rather than by a refresh loop that could fail.

## Recommended direction (do not build before measuring)

The design is already fail-safe, which is worth **not** breaking: adding a runtime
refresh that can overwrite committed data would be a regression against "avoid
overwriting valid data with incomplete updates". The value is in surfacing what
already exists:

1. **expose the header's date** as a constant (`catalog_generated_on()` or similar) so
   no second copy of the string can drift — the same rule as the width measurement.
2. **a `/catalog` command** printing the snapshot date, row count and provider count,
   with "run `scripts/regen_catalog.py` to refresh" when the date is stale.
3. Optionally, a scheduled CI job that runs the script and opens a PR when models.dev
   moves — that is "periodic refresh" without a runtime fetch path that can corrupt
   the store.

Item 2 is the smallest user-visible win and is testable with the existing frame-witness
pattern.

## LANDED (2026-10-14) — item 1: the date is one value

`pub const CATALOG_SNAPSHOT_DATE` in `crates/epsilon-llm/src/catalog.rs`, plus
`catalog_snapshot_date_matches_the_data`, which reads `catalog_data.rs`'s header and
asserts it carries the constant's date. **Control**: setting the constant to a wrong
date fails the test naming both files. 23 catalog tests pass; workspace clippy clean;
battery `gate-catalog-date-single-value-20261014` PASS 15/15, 2097 tests.

The date now exists exactly once as a *value* — previously it was prose in two files,
which had already drifted (2026-08-24 vs 2026-09-21, recorded in the test's own doc
comment). That drift class is now closed by a test rather than by attention.

**Next:** item 2, `/catalog`. Register the head once in
`crates/epsilon-contracts/src/command.rs` (invariant 4 — palette entries derive from
`COMMAND_HEADS`, so a hand-added entry is a defect), add the arm in
`epsilon-tui/src/app/commands.rs` printing the date, row count and provider count with
a refresh hint when stale, then a frame witness. The `/skills` command is the pattern
to follow — it already has a frame test.

**Status: item 1 done and proven; item 2 not started.**
