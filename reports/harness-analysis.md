# Harness Analysis — Phase 1

Four reference harnesses were audited from source, not from READMEs. For each harness the
architecture was traced through code: control flow followed from user input -> model call -> tool
execution -> back, and every claim below is anchored to a specific file under `references/`.

| # | Harness | Version | Language / Runtime | Shape |
|---|---------|---------|--------------------|-------|
| 1 | **pi** (`pi-0.84.2`) | 0.84.2 | TypeScript (Node/Bun), ESM-only, erasable syntax | Layered monorepo: `ai` -> `agent` -> `coding-agent` + own TUI lib |
| 2 | **DeepSeek Harness "DSH"** (`deepseek-harness-dsh-v0.1.1-rc.2`) | 0.1.1-rc.2 | TypeScript (Node >=22), pnpm monorepo, vendored Cordis DI kernel | Plugin-composition framework; ~150 packages; web-first UI |
| 3 | **Hermes Agent** (`hermes-agent-2026.8.19`) | 2026.8.19 | Python >=3.11,<3.14 (+ Node 22 for Ink TUI) | Modularized god-app; synchronous loop; SQLite state |
| 4 | **opencode** (`opencode-1.18.21`) | 1.18.21 | TypeScript on Bun 1.3.14, mid-migration to Effect v4 beta | Client/server product; SQLite+Drizzle; SolidJS/OpenTUI |

> Method note: each subfolder was treated as an independent codebase. Entry points were located from
> package manifests (`package.json` bins, `pyproject.toml` scripts); then the loop, tool dispatch,
> storage, prompt assembly, and permission code paths were read directly. Subagent-assisted sweeps
> were spot-verified against the named files.

## 1. pi (pi-0.84.2) — the port target

### Overview

Pi is a self-extensible coding agent built as a strict three-layer stack:

- **`@earendil-works/pi-ai`** (`packages/ai`) - unified multi-provider LLM API covering ~40
  providers (OpenAI, Anthropic, Google, Bedrock, OpenRouter, xAI, Moonshot, MiniMax...).
  Hand-written provider adapters over raw HTTP/SSE rather than vendor SDKs; generated model catalog
  (`src/models.generated.ts`, regenerated by `scripts/generate-models.ts`); OAuth flows (Anthropic,
  GitHub Copilot, OpenAI Codex, Kimi, xAI); retry policy (`utils/retry.ts`,
  `utils/provider-retry.ts`).
- **`@earendil-works/pi-agent-core`** (`packages/agent`) - the agent runtime: `agent-loop.ts`
  (pure loop functions), `agent.ts` (stateful `Agent` class), plus a reusable `harness/` layer:
  JSONL tree session store, compaction, skills loading, system-prompt building, and four core tools
  (read/bash/edit/write) with a file-mutation queue.
- **`@earendil-works/pi-coding-agent`** (`packages/coding-agent`) - the product CLI: interactive
  TUI mode, RPC mode, print mode (`src/modes/*`), extensions, themes, slash commands, project
  trust, plus additional tools (grep/find/ls).

Two supporting libraries matter for Epsilon: **`pi-tui`** (`packages/tui`), a from-scratch
differential-rendering terminal UI toolkit (component tree, layout engine in `layout.ts`,
keybindings, kill-ring, undo stack, alt-screen management), and **`pi-protocol`/`pi-client`**, the
RPC wire protocol used by non-TUI frontends.

### Architecture (redrawable)

```
+-------------------------- coding-agent (product) ---------------------------+
| modes/interactive (TUI)   modes/rpc   modes/print     extensions loader    |
|      | subscribe(AgentEvent)                     | jiti dynamic import     |
|      v                                           v                         |
| AgentSessionRuntime --> AgentSession --> ExtensionAPI (events/tools/UI)    |
+---------------+------------------------------------------------------------+
                | prompt() / steer() / followUp() / abort()
                v
+------------------------ agent-core (@pi/agent) -----------------------------+
| Agent (state machine; steering+followUp queues; awaited listeners)          |
|   runAgentLoop (agent-loop.ts)                                              |
|     outer loop: while follow-ups exist                                      |
|       inner loop: while toolCalls remain or steering pending                |
|         streamAssistantResponse(): transformContext -> convertToLlm ->      |
|           StreamFn(model, ctx, opts) -> fold AssistantMessageEvents         |
|         executeToolCalls(): prepare -> validate -> beforeToolCall ->        |
|           execute(onUpdate partials) -> afterToolCall -> ToolResultMessage  |
|     emits AgentEvent* ; Agent reduces events into state                     |
+---------------+-------------------------------------------------------------+
                | StreamFn contract ("never throws; failures encoded in stream")
                v
+------------------------------- pi-ai ---------------------------------------+
| Models.streamSimple(model, Context{systemPrompt,messages,tools}, options)   |
| provider adapters -> SSE parse -> AssistantMessageEventStream               |
+------------------------------------------------------------------------------+
```

Key mechanics, verified in source:

- **Two nested loops with queue drain points** (`packages/agent/src/agent-loop.ts:155-275`). The
  *inner* loop continues while the assistant message contained tool calls or steering messages are
  pending. The *outer* loop continues when follow-up messages arrive after the agent would
  otherwise stop. Steering = user interjects mid-run (drained after each turn's tools finish);
  followUp = queued work that must not preempt (drained only at a stop point). Both support
  `"all" | "one-at-a-time"` drain modes (`types.ts:44-50`; `PendingMessageQueue` at
  `agent.ts:125-159`).
- **Everything is an event.** The loop functions are pure: they take an emit callback and return
  new messages; the `Agent` class subscribes, reduces events into mutable state (`processEvents`,
  `agent.ts:544-591`), and awaits listeners in subscription order before the run settles. Events:
  `agent_start/end`, `turn_start/end`, `message_start/update/end`,
  `tool_execution_start/update/end`.
- **StreamFn failure contract** (`types.ts:22-32`): the model-call function *must not throw*;
  failures are delivered as a final `AssistantMessage` with `stopReason: "error" | "aborted"` plus
  `errorMessage`. Aborts, retries, and provider errors all flow through one channel.
- **Tool pipeline stages** (`agent-loop.ts:600-758`): lookup -> optional `prepareArguments` shim
  (pre-validation fixup for legacy arg shapes) -> TypeBox validation (`validateToolArguments` from
  pi-ai) -> `beforeToolCall` hook may return `{block, reason, terminate}` -> execute (abort signal +
  streaming `onUpdate` partial results) -> `afterToolCall` hook may override
  content/details/isError/usage -> normalized `ToolResultMessage`. Parallel execution preflights
  sequentially then runs concurrently; any batch containing a per-tool
  `executionMode: "sequential"` tool degrades the whole batch to sequential
  (`agent-loop.ts:411-426`).
- **Truncation-aware tool-call failing**: if `stopReason === "length"`, *every* tool call in that
  message fails with an instructive error instead of executing possibly-truncated JSON arguments
  (`failToolCallsFromTruncatedMessage`, `agent-loop.ts:381-406`).
- **Sessions are append-only JSONL trees** (`harness/session/jsonl/*`; entry types at
  `session/types.ts:14-74`): entries carry storage-assigned `seq`, `parentId`, `timestamp`. Entry
  kinds: `message`, `model_change`, `thinking_level_change`, `active_tools_change`, `compaction`,
  `branch_summary`, `custom`. Parent chaining makes fork/navigate tree operations data operations;
  `branch_summary` entries summarize abandoned branches; `custom` entries persist extension state
  without entering LLM context.
- **Compaction** (`harness/compaction/compaction.ts`): threshold-triggered summarization producing
  `{summary, tokensBefore, retainedTail, details}` stored as a compaction entry; file operations
  accumulate across prior compactions so summaries can name touched files; summary requests use a
  fresh session id and `cacheRetention: "none"` (`compaction.ts:102-122`) so they never poison the
  live conversation's prompt cache.
- **Extensions are same-process TS modules** loaded with jiti (`core/extensions/loader.ts`),
  receiving a wide `ExtensionAPI` (`extensions/types.ts:1198-1437`): typed event subscription
  (30+ events incl. `context`, `before_provider_request/headers`, `tool_call`/`tool_result`
  waterfalls with block/mutate semantics), `registerTool/Command/Shortcut/Flag/
  MessageRenderer/MarkdownTransformer/Provider`, full TUI access (dialogs, widgets, themes, editor
  replacement), session manipulation (`newSession/fork/navigateTree/switchSession`), and
  `sendMessage` with `deliverAs: "steer" | "followUp"` routed into the loop queues.
- **Skills follow the Agent Skills spec** (`core/skills.ts`): `SKILL.md` with YAML frontmatter;
  name/description validation (<=64 chars, `[a-z0-9-]`; description <=1024); discovery across
  global/project dirs honoring `.gitignore`-family ignore files; `disable-model-invocation` flag;
  injected into the system prompt only if the read tool exists (`system-prompt.ts:63-67,154-157`).
- **System prompt is assembled, not templated** (`system-prompt.ts:28-162`): identity paragraph ->
  available-tools list (only tools providing a one-line snippet) -> guidelines conditioned on which
  tools exist -> embedded docs pointers -> optional `appendSystemPrompt` -> `<project_context>`
  wrapping AGENTS.md-style files as `<project_instructions path="...">` blocks -> skills section ->
  cwd line.
- **Modes share one runtime**: interactive TUI, RPC (JSON lines over stdio for editors), print
  (`-p`) sit on the same `AgentSession`; the extension API exposes `mode` so extensions degrade
  gracefully outside the TUI.

### Strengths (with evidence)

1. **Layer discipline is real.** pi-ai cannot import agent-core; the only coupling between loop and
   providers is the `StreamFn` type (`types.ts:28-32`). The coding-agent consumes both through
   narrow surfaces, which is why a separate product (pi-chat, Slack automation) can reuse layers
   1-2 unchanged.
2. **Failure encoding beats exception plumbing.** StreamFn contract + `stopReason` on every
   assistant message means the loop needs no try/catch around model calls; error/aborted are
   handled uniformly at `agent-loop.ts:196-200`.
3. **Queue semantics are precise.** Steering vs follow-up with per-queue drain modes is specified
   down to *when* drains happen relative to `turn_end` and `shouldStopAfterTurn`
   (`types.ts:236-257`). Competing harnesses conflate these.
4. **Truncation-aware tool-call failing** prevents silent corruption from cut-off JSON arguments.
   None of the other three harnesses do this explicitly.
5. **The session format enables everything else.** Typed metadata entries (model change, thinking
   level, active tools) plus parent chaining make fork/navigate/branch-summary data operations, not
   hacks (`session/types.ts:22-65`).
6. **KV-cache-aware compaction** (`compaction.ts:110-115`): summary calls isolate routing and skip
   cache writes so they cannot invalidate the live cache. Hermes achieves similar ends via
   byte-stable prompt tiers; pi's explicit knob is cleaner.
7. **Supply-chain hardening as policy** (root README): exact-pinned direct deps,
   `min-release-age=2`, shrinkwrap for the CLI package, lifecycle-script allowlist,
   `--ignore-scripts` everywhere.
8. **Self-hosting docs**: the system prompt points the agent at pi's own documentation and tells it
   to read docs before implementing pi-related changes (`system-prompt.ts:131-138`) - the agent can
   explain and extend itself.

### Weaknesses (with evidence)

1. **No permission system by design.** Root README: "Pi does not include a built-in permission
   system." Isolation is delegated to external containerization docs
   (`docs/containerization.md`). No approve-once/approve-always gate, no path allowlists - a
   genuine interactive-UX gap vs opencode/DSH.
2. **Same-process extensions are a reliability risk.** A throwing extension listener disrupts a
   run; the loop awaits arbitrary listener promises (`agent.ts:586-590`). No isolation or timeout
   around extension handlers (contrast DSH's vm-sandboxed plugin runner).
3. **Small default tool surface.** Core harness ships read/bash/edit/write; grep/find/ls live in
   the coding-agent layer; no task/subagent tool, no todo tool, no web tools in-tree.
4. **System prompt assembly is string concatenation** with no section registry or snapshotting;
   extension-driven prompts (via `before_agent_start` returning `systemPrompt`,
   `extensions/types.ts:1102-1106`) can silently fight by full-string replacement.
5. **TypeScript runtime tax**: Node startup cost, GC pressure on long sessions, Bun-compile
   binary workarounds in `build:binary`. The full transcript lives in RAM (`Agent._state.messages`);
   compaction mitigates context growth but not memory of retained entries.
6. **Parallel tool execution has no concurrency cap** - `Promise.all` over all finalized calls
   (`agent-loop.ts:540-542`); a model emitting 20 parallel bash calls gets 20 concurrent processes.

### Patterns worth adopting in Epsilon

- Two-level loop with steering/follow-up queues and explicit drain modes.
- StreamFn "never throws; encode failures in-band" contract.
- Typed event stream as the only output of the loop; every UI is a reducer over events.
- Tool pipeline stages: prepareArguments shim -> schema validation -> before-gate -> execute with
  partial updates -> after-hook override.
- Append-only JSONL session tree with typed metadata entries and branch summaries.
- Compaction entries carrying retainedTail + file-operation details; cache-isolated summary calls.
- Fail-all-tool-calls-on-truncation rule.
- Agent Skills spec compliance (SKILL.md frontmatter, progressive disclosure via the read tool).
- Supply-chain policies (pinned deps, no install scripts).

### Anti-patterns to avoid in Epsilon

- Shipping without any permission/approval gate and deferring to "containerize it".
- Same-process unrestricted extensions without timeouts or isolation.
- Unbounded parallel tool fan-out.
- Prompt construction by ad-hoc string concatenation scattered across modules.

## 2. DeepSeek Harness "DSH" (v0.1.1-rc.2)

### Overview

DSH is DeepSeek's official agent harness, structured as a **plugin-composition framework**: a thin
kernel (vendored Cordis dependency-injection context) onto which ~150 `@deepseek-ai/dsh-*` packages
mount as plugins - including the agent loop itself. Composition is declared in YAML rows
(`cordis.yml`: `- id / name / config / disabled`), layered as profiles -> bundles -> patches. The
root AGENTS.md states the thesis plainly: "everything is a plugin"; behavior changes target event
waterfalls, never the loop.

Core spine (per `docs/architecture.md`): `packages/core/session` (append-only event log + derived
messages), `core/system-prompt` (section-based assembly), `core/tools` (guarded tool registry),
`core/agent` + `core/agent-loop` (`ReactLoopAgent`), `core/scope`, `llm/llm` (message/stream
vocabulary + adapter seam). Peripheral rings add persistence (JSONL + SQLite), shell/fs/subprocess/
terminal/e2b/sandbox, compaction, interaction (approvals), skill/mcp/hooks/acp/extensions, ~37 web
UI packages, and a Python SDK that drives the Node runtime over newline-delimited JSON-RPC on
stdio.

### Architecture (redrawable)

```
cordis.yml profile --> bundles (dsh-base...) --> patches --> plugin tree in Cordis Context
                                                                      |
+----------------------------- agent-plane ---------------------------+
| ReactLoopAgent (core/agent-loop/src/agent.ts)                       |
|   Phase = idle | maintenance | running(turn, step)                  |
|   kick(): while await this.turn()                                   |
|     turn(): log turn/start                                          |
|       step(): claim durable inbox ('next-step'|'next-turn' lanes)   |
|         assemble prompt sections + schemas (ctx.systemPrompt)       |
|         waterfall agent/pre-step (reject/rewrite claimed msgs)      |
|         buildRequest(): frozen GenerateOptions; agent/request       |
|         llm.stream(request) -> assistant/chunk* -> BlockAssembler   |
|           -> durable assistant/message (sourceEventSeqs)            |
|         tool/call* -> pre-execute -> guards -> execute              |
|           -> post-execute -> tool/result*                           |
|     until stop; turn/end {completed|max-tokens|blocked|aborted|err} |
| Invariant: "model-visible means logged"                             |
+----------------------------------------------------------------------+
```

Distinctive verified mechanics:

- **Durable two-lane inbox** (`core/agent/src/inbox.ts`): queued user input persists as session
  events (`agent/inbox/spliced`), split into next-turn vs next-step targets. Crash-safe by
  construction; the phase state machine (`idle | maintenance | running`, `agent.ts:38-47`) resumes
  from the log.
- **Event-sourced everything**: raw `assistant/chunk` events, retry ledger, approval audits -
  all durable. Any UI/replay/SDK rebuilds exact requests from the log. Streaming abort commits
  partial content as an `interrupted: true` assistant message citing chunk seqs
  (`agent-loop/src/agent.ts:354-370`).
- **Tool pipeline with monotonic guards** (`core/tools/src/index.ts`): ordered stages -
  `tools/pre-execute` waterfall (allow/deny/**ask**) -> **monotonic guards** (may only deny, never
  force-allow, so listener order cannot resurrect a denied call; lines 700-711) -> around-dispatch
  `tools/execute` waterfall (timeout/retry wrappers; wrapper signals fused with caller signal so
  cancellation cannot be detached, `fuseToolSignals` lines 1889-1916) -> tool body ->
  `tools/post-execute` (accept/replace/block) -> frozen lossless-JSON result emit. `ask` resolves
  through the optional approval service and **fails closed** when absent.
- **Code Mode** (`core/tools/src/code-mode.ts`): `mode: 'native' | 'code' | 'both'`. Under code,
  the only directly callable tool is a reserved `run_code` transport; a generated SDK section
  teaches the model to invoke every other tool as `await tools.name(args)` inside one TypeScript
  program (Python renderer exists too). Direct calls naming other tools deterministically fail
  before policy with an instructive UNKNOWN_TOOL message; sub-dispatches re-enter the complete
  guarded pipeline and log `tool/code-dispatch-start|tool/code-dispatch`.
- **Scheduling**: `executeToolCalls` (`agent-loop/src/tool-calls.ts`) classifies calls via
  `ctx.tools.executionMode()` / per-tool `isConcurrencySafe(args)`; parallel-safe calls fill a
  bounded rolling pool (`maxParallelToolCalls`), exclusive calls form barriers; results commit in
  model order; aborted un-started calls get synthetic ordered error results so replay stays valid.
- **Surface shadowing compaction** (`core/session/src/surface.ts` +
  `compaction/compaction-basic`): the human transcript keeps append-origin events while the
  model-visible surface supports replacement/shadowing of ranges. Compaction summarizes a selected
  range with a direct one-shot stream whose prefix reuses the conversation's own system prompt,
  tools, and messages so the provider KV cache survives (JSDoc at compaction-basic
  lines 226-235); the summary + shadowed seq range are recorded durably. Two triggers: token
  pressure checked in an `agent/pre-step` listener, and `CONTEXT_WINDOW_EXCEEDED` recovery in an
  `agent/request-error` listener that prunes, compacts, and returns `{kind:'retry'}` bounded by
  `maxOverflowRetries`. A model-free pass first: tool-result pruning (default threshold 8192
  chars, keep head 4096 / tail 1024).
- **Spill seam** (`packages/spill/*`): oversized tool outputs never enter context wholesale;
  text persists behind a locator + retrieval hint handed to the model instead.
- **Sandboxing** (`packages/sandbox/sandbox/src/index.ts`): abstract
  `SandboxProvider.confine(argv, policy)` with modes `'read-only' | 'workspace-write' |
  'danger-full-access'`; **policy rides each call**, not the provider. Backends probed in order:
  bubblewrap -> Landlock (first-party native addon under `native/landlock-run`) -> macOS
  Seatbelt/sandbox-exec -> Windows ACL restricted-token runner (per-session random private temp
  dir + SID). Fail-closed: `SandboxUnavailableError` refuses to run unconfined (lines 131-139).
  Every wrap returns backend-specific `denialSignatures` (EROFS/EACCES/EPERM dialects) so consumers
  distinguish "sandbox blocked it" from "command failed". **In-band escalation protocol**
  (`escalation.ts`): the bash tool description teaches the model to retry once with
  `sandbox_permissions` (narrowest wider mode) + one-sentence justification; the retry raises a real
  approval prompt rather than a chat detour.
- **Reliability** (`packages/llm/llm-retry`): exponential backoff with jitter honoring provider
  `retryAfterMs` up to a cap; modes normal/always; every scheduled wait is **durably logged before
  it starts** and resume recomputes attempts by scanning the log - crash-safe retry accounting.
  Typed sticky turn endings (`max-tokens` wins over later completed steps); repeat-tool reminder
  guard injects escalating advisories at 3/5/8 identical consecutive calls (advisory only);
  session repair helpers close interrupted turns after crashes (`core/session/src/repair.ts`).
- **Prompt construction** (`core/system-prompt`): ordered unique-name sections with scoped
  shadowing; `-100` fixed harness identity; `0` replaceable persona; `99` Code-Mode statement;
  `100-199` per-tool guidance; exactly one optional `complete: true` section may replace all.
  Strict hand-rolled `{{variable}}` interpolation that throws on malformed references. Dynamic
  runtime contexts render into a supersede-on-change snapshot appended after retained history
  ("This snapshot supersedes earlier runtime-context snapshots") - cache-friendly.
  AGENTS.md loading lives in `context/agent-instructions`: baseline instructions enter durable
  context pre-first-request; nested instruction files touched later by read/write/edit tools are
  injected into the inbox via post-execute tracking; byte budgets render truncation notices as
  `<system-reminder>` blocks.
- **Config/extensibility**: YAML profiles/bundles/patches with `!!js` JS expressions permitted only
  under plugin config and entry `disabled`; agent presets (`apps/cli/config/agent-presets/{minimal,
  standard,code,cordis}`) compose whole products; skills packages; MCP client registering tools as
  `mcp__<server>__<name>`; Claude Code/Codex **hook bridges** for cross-harness compatibility; ACP
  server for editors; self-modification toolset `cordis_define/run/inspect/stop/undefine`
  (vm-sandboxed, opt-in).

### Strengths (with evidence)

1. **Best-in-class sandboxing story.** Four platform backends including Windows ACL restricted
   tokens, fail-closed semantics, per-call policy, denial-dialect signatures, and an in-band
   escalation protocol that converts sandbox denials into real approval prompts. Nothing else here
   comes close (opencode has pattern permissions but no OS confinement; pi explicitly opts out).
2. **Monotonic guard pipeline** is an elegant answer to plugin-ordering attacks: deny-only guards
   make security decisions order-independent.
3. **Event sourcing with surface shadowing** gives non-destructive compaction: audit keeps the
   human transcript while the model view is rewritten; replay/recovery become trivial.
4. **Durable inbox + durable retry ledger** survive restarts mid-run - the only harness of the four
   whose steering input and retry accounting are crash-safe by design.
5. **Code Mode** collapses tool-schema bloat into one executable program - the same insight Hermes'
   AGENTS.md calls the "Footprint Ladder", taken to its logical extreme, with sub-dispatches still
   passing the guarded pipeline.
6. **Cross-platform rigor**: Windows is a first-class target (ACL runner, ConPTY PTY, koffi-backed
   write-through JSONL durability via MoveFileExW).
7. **Compatibility pragmatism**: hook bridges for Claude Code and Codex hooks; delegation providers
   that shell out to competitor CLIs behind one seam.

### Weaknesses (with evidence)

1. **Enormous complexity budget.** ~150 packages, a vendored-and-forked DI framework (Cordis
   4.0.0-rc.7 with local patches to `fiber.ts`), two-level workspace layout, realms/isolate scoping.
   Onboarding cost is extreme; even the docs need bilingual link-checking machinery.
2. **Pre-release maturity**: v0.1.1-rc.2; the architecture documents aspirational invariants
   ("model-visible means logged" enforced by runtime assertion) whose long-term costs (log volume:
   every chunk persisted) are unknown at scale.
3. **YAML + `!!js` config** permits arbitrary JS expressions in config evaluation - powerful, but
   an arbitrary-code-execution vector in a file users copy from the internet.
4. **Web-first UI** (~37 React packages) with a thin CLI means terminal-first developers get the
   least-polished surface of the four.
5. **Vendored dependencies** trade supply-chain risk for maintenance burden; upstream Cordis fixes
   must be ported by hand.

### Patterns worth adopting in Epsilon

- Monotonic (deny-only) guard stage in the tool pipeline.
- Per-call sandbox policy + fail-closed confinement + denial signatures distinguishing sandbox
  denial from command failure; in-band escalation with justification.
- Surface shadowing for compaction (keep human log intact).
- Durable steering inbox; typed sticky turn-end reasons; durable retry ledger keyed by
  (turn, step, provider).
- Spill-to-disk for oversized outputs with locators.
- Bounded parallel pool with concurrency classification (`isConcurrencySafe`).
- Repeat-call advisory guard (loop breaker) as telemetry-grade safety.
- Section-based system prompt with stable ordering and cache-conscious runtime snapshots.

### Anti-patterns to avoid in Epsilon

- Vendoring/forking foundational frameworks.
- Plugin-everything maximalism where a handful of well-chosen seams would do.
- Arbitrary code (JS expressions) inside configuration files.
- Persisting every raw streaming chunk forever without tiering.

## 3. Hermes Agent (2026.8.19)

### Overview

Hermes is a Python-first, production-hardened personal/omni-channel agent: a synchronous,
OpenAI-chat-completions-shaped core wrapped in an enormous reliability and extensibility apparatus.
Root-level scripts (`run_agent.py` 9,205 lines; `cli.py` 21,447 lines; `hermes_state.py` 13,114
lines) are god-file shells that forward into a modularized core under `agent/` (~148,700 lines
across ~170 modules; e.g. `conversation_loop.py` 8,411 lines, `context_compressor.py` 8,027 lines).
Node.js appears only for the Ink (React 19) TUI and web dashboard; Python drives everything else.

### Architecture (redrawable)

```
cli.py (Rich + prompt_toolkit REPL)   ui-tui (Ink/React) ==JSON-RPC/stdio==> tui_gateway
        |                                          |
        v                                          v
run_agent.AIAgent.chat() -> run_conversation forwarder
        v
agent/conversation_loop.py::run_conversation   [synchronous]
  build_turn_context(): stdio guard, retry-counter reset, sanitize user msg,
    todo/nudge hydration, system-prompt restore-or-build, preflight compression,
    pre_llm_call plugin hook, external-memory prefetch
  while api_call_count < max_iterations and budget.remaining > 0:
    if interrupt_requested: exit("interrupted_by_user")
    consume iteration budget
    retry sub-loop (max_retries): streaming chat.completions.create(...)
      via agent/chat_completion_helpers.interruptible_streaming_api_call
      chunks -> _accept_stream_chunk gate (single-writer across fallbacks)
      deltas -> stream_delta_callback
    _execute_tool_calls(...) -> results appended as role:"tool" messages
  final content -> {"final_response", "messages", "api_calls"}
```

Key mechanics, verified in source:

- **Tool registry**: singleton `ToolRegistry` (`tools/registry.py`). Tools self-register at import:
  `registry.register(name=..., toolset=..., schema={...}, handler=..., check_fn=...,
  requires_env=[...])`. Discovery is AST-based (`discover_builtin_tools()` scans each `tools/*.py`
  for a top-level `registry.register(` call, ~145 ms over ~100 files, memoized on disk). Schemas
  are hand-written JSON-schema dicts per tool file. `get_definitions()` filters by TTL-cached
  `check_fn` availability probes (with failure-grace so one transient probe timeout doesn't strip a
  toolset) and emits native OpenAI function-calling entries
  (`{"type":"function","function":schema}` at registry.py:1071). Dispatch:
  `model_tools.handle_function_call` (:1192) coerces arg types, runs plugin hooks/middleware, then
  `registry.dispatch` (:1109) invokes the handler (bridging coroutines via `_run_async`) and
  normalizes to JSON strings.
- **Toolsets** (`toolsets.py`): `_HERMES_CORE_TOOLS` (web_search, terminal, process, read/write/
  patch/search_files, browser_*, todo, memory, execute_code, delegate_task, cronjob...) gated by
  enabled toolsets; progressive disclosure for big catalogs via `tools/tool_search.py`.
- **State**: SQLite WAL DB at `~/.hermes/state.db` (`hermes_state.py::SessionDB`, schema in
  `hermes_state_common.py::SCHEMA_SQL`): sessions (~50 columns incl. model config, token/cost
  counters, compression bookkeeping), messages (role, content, tool_calls JSON, reasoning fields,
  `compacted`, `api_content`), session_model_usage, compression_locks, session_turn_leases,
  async_delegations, plus FTS5 (+trigram) virtual tables for full-text search. WAL with size-limit
  pragmas; macOS-only `synchronous=FULL` enforcement.
- **Context compaction** (`agent/context_compressor.py::ContextCompressor`): documented five-step
  strategy - prune old tool results (no LLM), protect head (system prompt + first exchange),
  protect tail by token budget, summarize middle with structured prompt, iteratively update the
  prior summary on re-compaction. Trigger = context length x threshold_percent (default 0.50;
  small-context models floored at 0.75); target_ratio 0.20; protect_last_n 20; auxiliary LLM does
  summarization with anti-thrash cooldowns and SQLite-held compression locks.
- **Prompt construction as cache tiers** (`agent/system_prompt.py::build_system_prompt_parts`,
  :340): three ordered byte-stable tiers - stable (identity/SOUL.md, help guidance, environment),
  context (caller system message + AGENTS.md/.cursorrules context files capped at
  CONTEXT_FILE_MAX_CHARS=20,000 or dynamic), volatile (skills index, memory snapshot, USER.md,
  timestamp/session/model line). Built once per session; rebuilt only on compression. The
  `api_content` sidecar (`agent/turn_context.py:59-86`) stores exactly what was sent each turn so
  "what turn N sends must be what turn N+1 replays"; prompts are persisted in SQLite and restored
  verbatim across restarts.
- **Approvals/sandboxing** (`tools/approval.py`, 5,498 lines): DANGEROUS_PATTERNS regexes +
  `detect_dangerous_command()`; per-session approval state keyed by contextvars (fixes GHSA-
  96vc-wcxf-jjff identity confusion); interactive + gateway prompting; LLM-assisted "smart
  approval" of low-risk commands; permanent allowlist persisted to config. YOLO mode frozen at
  import time (`_YOLO_MODE_FROZEN`, :34-37) so skills cannot flip it mid-process. Execution
  environments (`tools/environments/base.py`): spawn-per-call model - every command is a fresh
  `bash -c`; session snapshot (env/functions/aliases) captured once and re-sourced; CWD persists
  via in-band stdout markers (remote) or temp file (local). Backends: local, docker, ssh, modal,
  daytona, singularity, vercel_sandbox.
- **Providers/fallback**: provider profiles are plugins (`plugins/model-providers/`, 36 providers);
  `ProviderProfile` dataclass (`providers/base.py`) declares api_mode, env_vars, auth_type
  (api_key | oauth_device_code | oauth_external | copilot | aws_sdk), fallback_models, fixed
  temperature, default_aux_model. `chat_completion_helpers.try_activate_fallback` walks a
  configured fallback chain on rate-limit/overload/connection failures classified by
  `error_classifier`, restoring the primary next turn. Transports per wire protocol live in
  `agent/transports/` (chat_completions, anthropic native, bedrock, codex responses).
- **Extensibility**: plugins from repo/`~/.hermes`/project dirs plus pip entry points
  (`hermes_agent.plugins` group); hook points pre/post_tool_call, pre/post_llm_call,
  on_session_start/end; tools registration with scoped overlays (override opt-in). Skills:
  bundled `skills/` + install-on-demand `optional-skills/` via Skills Hub; SKILL.md YAML
  frontmatter (name, description <=60 chars, version, platforms, tags) with references/templates/
  scripts; explicit three-stage progressive disclosure (skills_list -> skill_view -> linked files
  on demand). MCP client (`tools/mcp_tool.py`: stdio/HTTP-streamable/SSE, OAuth helpers, dynamic
  refresh) and MCP server side (`mcp_serve.py` exposes messaging conversations as MCP tools).
- **Reliability craft**: exact-pinned dependencies post supply-chain incident ("Mini Shai-Hulud"
  policy comment in pyproject.toml:19-39); iteration budget + grace calls; stale-stream circuit
  breakers; buffered retry-status noise dropped on success; ephemeral scaffolding flags excluded
  from persistence so resumed sessions never replay internal recovery context; durable session-turn
  leases (`session_turn_leases` table) serializing load->run->flush across CLI/Desktop/gateway/cron
  processes with fail-closed acquisition.
- **UI**: Rich + prompt_toolkit REPL with slash-command registry; Ink/React TUI over JSON-RPC
  stdio gateway; asyncio messaging gateway (~20 platforms incl. telegram/discord/slack/whatsapp);
  ACP adapter exposing sessions/tools/permission prompts to editors (VS Code/Zed/JetBrains).

### Strengths (with evidence)

1. **Prompt caching treated as an architectural invariant**: byte-stable three-tier prompts,
   persisted verbatim, restored across restarts, with the api_content sidecar guaranteeing replay
   fidelity. This is the deepest cache discipline of the four.
2. **Operational hardening born from incidents**, each documented: SQLite pinned/rebuilt in Docker
   because Debian's build has the WAL-reset corruption bug (FTS5 runtime self-test added);
   Windows UTF-8 bootstrap module plus a repo-wide ruff encoding lint born from "three separate
   Windows sandbox regressions"; s6 zombie reaping for MCP subprocesses.
3. **Cross-process correctness**: turn leases make CLI/TUI/gateway/cron coexist safely on one
   SQLite state file - unique among the four.
4. **Provider fallback chains** with error classification and per-turn primary restoration.
5. **Skill ecosystem with governance**: hub distribution, platform gating, and the "Curator" that
   auto-archives unused agent-authored skills (never deletes; pin-exempt).
6. **Security thinking in depth**: YOLO freeze against in-process escalation; contextvar approval
   identity fixing a published GHSA; webhook toolsets constrained read-only against prompt
   injection; SSRF-guarded skill fetches with quarantine.

### Weaknesses (with evidence)

1. **Monolith gravity**: 21k-line cli.py, 13k-line state module, 9k-line run_agent even after the
   modularization pass (forwarders preserved for test-patch contracts). Change risk concentrates.
2. **Synchronous loop**: `run_conversation` is plain `def`; concurrency exists only inside tool
   handlers via `_run_async` bridges and in the gateway. Parallelism ceiling is structural.
3. **Hand-written JSON schemas per tool** drift from handler signatures without generation.
4. **Regex-based dangerous-command detection** as the primary safety layer is fundamentally
   spoofable (quoting, encodings, new tools); contrast DSH's OS-level confinement or opencode's
   parsed-command permission patterns.
5. **openai SDK as universal shim**: Anthropic/Gemini/Bedrock reached through adapters over the
   OpenAI SDK shape; impedance mismatches surface as special cases in chunk accumulation
   (`chat_completion_helpers.py:4203-4237` documents delta quirks).

### Patterns worth adopting in Epsilon

- Three-tier byte-stable prompt assembly (stable/context/volatile) with rebuild-only-on-compaction.
- api_content sidecar / replay fidelity invariant.
- Session-turn leases for multi-process safety around one state store.
- check_fn availability probes with TTL + failure grace.
- Iteratively-updated rolling summary (update prior summary rather than re-summarize from scratch).
- Ephemeral scaffolding flags excluded from persistence.
- Provider fallback chains driven by error classification.
- Skills progressive disclosure (list -> view -> linked files).

### Anti-patterns to avoid in Epsilon

- God-files; forwarder layers to preserve legacy test patches.
- Regex string-matching as a security boundary.
- A single vendor SDK shape as the universal adapter.
- Synchronous-only core loop.

## 4. opencode (1.18.21)

### Overview

opencode is a client/server coding-agent product: a Bun-runtime TypeScript monorepo (32 packages)
whose kernel persists everything in SQLite (Drizzle migrations) and serves typed HTTP/SSE APIs that
thin frontends consume - OpenTUI/SolidJS terminal app, Electron desktop, web app, editor clients
via ACP. It is mid-migration onto **Effect v4 beta** (patched beta dependency), with two
architecture generations coexisting: classic logic in `packages/opencode/src` (session/, tool/,
permission/) and "V2" machinery in `packages/core`.

### Architecture (redrawable)

```
TUI(SolidJS/OpenTUI)  Desktop(Electron)  Web  Editors(ACP)  Plugins(SDK client)
        \                 |                 |        |            /
         +--------- local HTTP/SSE server (packages/opencode/src/server) +
                              |  Effect HttpApi + OpenAPI -> sdk/js
                              v
                    SessionPrompt.Service.loop()  (session/prompt.ts)
                      run-state.ts: ensureRunning - one loop per session
                      while(true):
                        msgs = MessageV2.filterCompacted(sessionID)
                        latest = MessageV2.latest(msgs)  # pending tasks:
                            subtask | compaction queue items popped 1/iter
                        create assistant msg; processor.create(...)
                        tools = SessionTools.resolve(agent, session, model)
                        system = [env, instructions, mcpInstructions, skills]
                        result = processor.process({messages,...})   # one LLM turn
                          processor.ts: LLMEvents -> persisted parts
                          retry policy; overflow -> needsCompaction
                        result: compact -> summarize & loop | stop | continue
                      forked: compaction.prune(...) at loop end
```

Key mechanics, verified in source:

- **Tools** (`packages/opencode/src/tool/tool.ts`): Effect services created via
  `Tool.define(id, initEffect)`; resolved `Def` = `{id, description, parameters (Effect Schema
  decoder; zod only at plugin boundary), jsonSchema?, execute(args, ctx) -> Effect<ExecuteResult>,
  formatValidationError?}`. `wrap()` hoists schema decoding for speed, converts bad args into a
  model-friendly `InvalidArgumentsError`, applies output truncation, adds OTEL spans. Tool
  `Context` carries sessionID/messageID/agent/**abort AbortSignal**/extra/prior messages/a
  streaming metadata updater/`ask()` for permissions. Registry (`registry.ts`) instantiates built-
  ins plus custom `{tool,tools}/*.{js,ts}` files and plugin-provided tools. Built-in ids: shell,
  read, glob, grep, edit, write, task (subagent), fetch, todo, search, skill, question, invalid
  (placeholder for unknown calls), patch/apply_patch (gpt models only, where edit/write hide),
  lsp + execute (experimental), plan-exit. LLM-facing descriptions live in sibling `.txt` files -
  clean separation of prose from code.
- **Permission system** (`permission/index.ts`): flat rulesets of `{permission, pattern, action}`;
  evaluation is last-match-wins wildcard:
  `rulesets.flat().findLast(rule => match(permission) && match(pattern)) ?? {action:"ask"}`.
  Any deny fails immediately; any non-allow publishes `Event.Asked` and awaits a Deferred;
  replies support once/always (always pushes an allow rule and auto-resolves compatible pending
  asks)/reject (with optional corrected-input feedback). Defaults: reads allowed but `.env` asks;
  external directories ask; doom_loop asks. The shell tool parses commands with **tree-sitter bash
  AND powershell grammars** to extract touched paths and per-command prefixes before asking
  (`tool/shell.ts:620-628`), making patterns precise instead of regex-guessed.
- **Loop specifics**: overflow accounting (`session/overflow.ts`) compares total tokens vs usable
  input window minus reservation; on overflow or ContextOverflowError the processor returns
  "compact". Compaction (`session/compaction.ts`): PRUNE_MINIMUM 20k tokens, protected recent tail
  clamped 2k-15k, tool outputs truncated to 2k chars in serialized transcript, skill outputs never
  pruned; a hidden `compaction` agent writes a strict Markdown summary template (Objective /
  Important Details / Work State / Next Move / Relevant Files, 4096 max output tokens);
  `filterCompacted` reorders history as [compaction-user, summary, retained tail..., continue-user];
  if the original prompt overflowed mid-turn it is replayed as a fresh user message.
- **Doom-loop brake** (`processor.ts:358-380`): 3 consecutive identical tool calls trigger a
  `doom_loop` permission ask. Orphaned interrupted tool parts are detected on resume so cleanup
  marks don't cause assistant prefill requests (`prompt.ts:96-100`).
- **Snapshots/undo**: shadow git repo per project (`snapshot/index.ts`), tracked before each step;
  patches recorded as message parts power `SessionRevert.revert/unrevert` with computed diffs;
  pruned after 7 days.
- **Agents**: built-ins build (default), plan (edits denied except plan files), general, explore
  (read+search only), compaction, title/summarize helpers; each carries mode/permissions/model/
  temperature/topP/prompt/steps cap/hidden; custom agents from config or Markdown; AI-authored
  agents generated via structured output.
- **Plugins** (`packages/plugin/src/index.ts` Hooks): event, config, tool map, auth, provider,
  chat.message, chat.params (temperature/topP/topK/maxOutputTokens mutation), permission.ask,
  tool.execute.before/after, tool.definition, shell.env, command.execute.before, experimental
  message-transform and session-compacting hooks. Plugin npm deps installed on demand; several
  first-party plugins ship as provider-auth glue.
- **MCP**: full client (stdio/SSE/streamable-HTTP via official SDK), OAuth with callback server,
  roots capability, caches, ToolsChanged notifications, resource reads (10MB cap; images/PDFs
  attached as data URLs). **LSP**: language servers spawned per project; post-edit diagnostics fed
  back to the model; formatters run after edits.
- **Instruction loading** (`session/instruction.ts`): globals `~/.config/opencode/AGENTS.md` and
  `~/.claude/CLAUDE.md`; project walk upward first-match-wins per file type (AGENTS.md | CLAUDE.md
  | CONTEXT.md-deprecated); config may add globs and URLs (5s timeout). Lazy attachment: nearby
  AGENTS.md/CLAUDE.md attach when Read touches files in subdirectories. System prompt bodies are
  per-model `.txt` files selected by id sniffing (anthropic/gpt/gemini/kimi/codex/default...).
- **Storage/events**: SQLite WAL via bun:sqlite (node fallback mapped by `"#db"` import); durable
  sequenced EventV2 rows fanned out through Effect PubSub, bridged to a GlobalBus tagged by
  {directory, project, workspace} for SSE consumers with sync payloads for replica maintenance.
- **Retry**: up to 5 attempts, exponential 2^n seconds with +-25% jitter honoring Retry-After;
  abort propagation kills children with forceKillAfter 3s; SSE header/chunk timeouts wrap provider
  streams.

### Strengths (with evidence)

1. **The most usable permission system of the four**: declarative last-match-wins wildcards,
   ask/deny/allow, once/always UX, corrected-input feedback, sensible defaults (.env asks,
   external dirs ask, doom loops ask), and tree-sitter-derived patterns so rules match real
   command semantics.
2. **Shadow-git snapshots** give time-travel undo of every step - unique here.
3. **Server/client split done right**: one typed API (OpenAPI-generated SDK) consumed by all
   frontends; enables headless/embedded use and clean multi-client futures.
4. **Overflow handling is a designed path**: reserved-token accounting, dedicated compaction agent
   with strict template, history reorder, mid-turn replay - not an afterthought.
5. **models.dev catalog integration** keeps model metadata fresh without hardcoding; AI SDK v6
   gives broad provider reach cheaply.
6. **Diagnostics-aware editing**: post-edit LSP diagnostics flow back to the model; formatters run
   automatically.

### Weaknesses (with evidence)

1. **Beta framework dependence**: `effect@4.0.0-beta.83` (patched!) underpins the whole kernel -
   churn risk directly beneath the product; learning curve tax on contributors.
2. **Two generations coexist**: v1 storage migration code paths alongside V2 core schemas; dual
   bus systems (typed EventV2 + untyped GlobalBus EventEmitter). Cognitive load and drift risk.
3. **Huge dependency surface**: ~20 @ai-sdk providers, tree-sitter grammars, PTY, watchers -
   large audit burden; Bun-first features (bun:sqlite) need fallback maps for Node.
4. **Model-id sniffing for prompt selection** (`system.ts`: includes("gpt") etc.) breaks silently
   on new model families.
5. **No OS-level sandbox**: permissions gate intent, not capability; a determined escape (e.g.,
   command referencing unlisted paths via indirection) is possible. Confinement experiments exist
   (codemode package, cloud containers) but nothing default.

### Patterns worth adopting in Epsilon

- Last-match-wins wildcard permission rulesets with ask/deny/allow and once/always memory.
- Tree-sitter (or equivalent parser-based) command analysis feeding permission patterns.
- Structured compaction template + protected-tail token clamp + mid-turn replay on overflow.
- Doom-loop detector tied into the permission gate.
- `.txt` description files separating tool prose from tool code.
- Reserved-token accounting for context budgets (usable = limit - reserved).
- Task-queue items inside the loop (subtask, compaction) processed one per iteration.
- Shadow-VCS snapshots for undo (adapt: git-free content-addressed store).
- OpenAPI-generated SDK over a local server for multi-frontend reuse.

### Anti-patterns to avoid in Epsilon

- Building on beta frameworks or patched transitive deps.
- Carrying two architecture generations at once.
- Model-id substring sniffing for behavior selection.
- Untyped global event emitter alongside the typed bus.

## 5. Cross-harness observations recorded during analysis

(Full comparison lives in `comparative-analysis.md`; these are notes captured while reading.)

1. **Convergent evolution**: all four independently arrived at (a) streaming-first model calls,
   (b) append-only persistence, (c) summarization-based compaction with a protected recent tail,
   (d) tool schemas validated before execution, and (e) some form of user-queueing mid-run
   (steering). These are table stakes for a modern harness.
2. **Divergent philosophies on safety**: pi = "bring your own sandbox" (none built-in); opencode =
   intent-level permission gates (patterns + prompts); DSH = OS-level confinement with in-band
   escalation; Hermes = regex danger detection + LLM-assisted approval. Epsilon should combine the
   two strongest layers: opencode-style declarative gates *and* DSH-style fail-closed confinement,
   rather than choosing one.
3. **Cache discipline separates mature harnesses from young ones**: pi (cacheRetention knobs),
   Hermes (byte-stable tiers + api_content sidecar), DSH (cache-preserving summary calls) treat
   prompt-cache preservation as a first-class invariant. opencode handles it implicitly via AI SDK.
4. **The loop is small everywhere**; everything else is session management, tool plumbing, and UX.
   pi's entire loop is ~800 lines including comments. Complexity lives at the edges.
5. **Extension isolation is unsolved in three of four**: pi same-process TS, opencode same-process
   TS plugins, Hermes same-process Python imports. Only DSH sandboxes extension code (vm), and it
   is opt-in/experimental. Epsilon has an opportunity to make process-isolated extensions cheap
   (OS processes are Rust's native unit of isolation).
6. **Windows support is a real differentiator**: DSH (ACL runner, ConPTY) and Hermes (UTF-8
   bootstrap, encoding lint born from regressions) invested; pi/opencode mostly target POSIX.
   Epsilon developing on Windows should treat win32 as first-class.
