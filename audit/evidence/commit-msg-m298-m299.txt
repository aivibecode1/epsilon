fix(m298): /restore deleted a file the user had edited after the agent created it

Reverting an agent-CREATED file called remove_file with no content check at
all. The agent creates a file, the user types their own work into it, they ask
to undo the creation, and /restore deletes their work with it - after a preview
that said only DELETE, which is accurate about the outcome and silent about
whose work was in the file.

The second finding is what made it fixable rather than merely reportable:
amend_with_post_image skipped any entry whose blob was None, documented as
"nothing was captured to amend". That is true of a SKIPPED capture and false
of a CREATION, which is the other way to have no blob. So creations were never
amended and the deletion guard had nothing to compare against. One condition
(&& newest.existed) and one call - no schema change, no migration.

ADR-023's "still open" paragraph said the DELETE preview was the honest
mitigation. It was not: the preview is generated from the entry and cannot see
the user's later edit, which is the only fact that mattered. ADR-026.

Negative controls run on both halves separately: removing only the guard call
fails the new test; restoring only the skip condition fails the two
untouched-creation tests, which is the point of having them.

Two fixtures were lying about the product - they recorded a creation and wrote
the file without the amendment every real write performs. They now mirror it,
which is the M277c lesson applied a second time.

fix(m299): the owner's report - "the output of the model is not shown", and
switching models "keeps reverting to another" - was four separate defects.

1. The answer and a harness notice drew the SAME gutter glyph, and colour was
   the only thing separating them. A plain console draws no band, so the
   model's reply rendered as "* something" and a transcript looked like it had
   no prose. The test meant to prevent this asserted the collision instead: it
   named the pair in a comment and pinned both to the same character. The
   frame was rendered and read at 80x24 and 100x30 before claiming the fix.

2. A /model switch was written to config.toml and nowhere else, so a resume
   preferred the session's model - which could only ever be the previous run's,
   because nothing in production recorded the switch. Measured on the
   reporter's machine: config said deepseek-flash, the session said
   deepseek/deepseek-chat-v3.1, and the launch took the session's.

3. A rejected API key said only "invalid api key", so a reader could not tell
   the model had produced no reply at all. One line now says so. A rate limit
   deliberately does not get it - that would send a reader to re-check a good
   key.

4. The picker's recent list re-read a shared machine-wide config file, and was
   skipped entirely when that file could not be written. Two tests asserting
   it failed on UNMODIFIED code; proved by stashing and re-running.

Also: two ConPTY tests were failing because with no provider flag the launch
auto-detects, so on a machine holding a key they had become live-network
tests. They now pin --provider faux.
