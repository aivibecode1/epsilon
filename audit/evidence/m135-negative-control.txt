M135 NEGATIVE CONTROL — the fix reverted, the defect reproduced
==============================================================

Purpose
-------
M135 closes a second route into F01: `edit` recorded its own success through
`read_log::record_write`, whose contract ("the bytes just written are known in
full") is true of `write` and false of a targeted replacement. It *set* the
file's "wholly seen" state, so a model could read 20 lines of a 200-line file,
edit one of them, and then replace all 200.

This file exists because an independent review (audit/evidence/m135-review.md,
blocker B1) found the control asserted as executed in four documents while no
log of it existed anywhere in the tree. This is that log. The control was
re-run on the final bytes so the recorded output matches the code that ships.

Machine: Windows 10, 2026-09-25
Target:   CARGO_TARGET_DIR outside the repo (Avira pins the in-repo artifact path
          — see agents/memory/next-hardening.md)
Build:    CARGO_BUILD_JOBS=1

What was reverted
-----------------
crates/epsilon-tools/src/files.rs, both successful targeted-edit call sites:

    -  crate::read_log::record_edit(&ctx.observation_scope, &path);
    +  crate::read_log::record_write(&ctx.observation_scope, &path);

  (line 555, the single-edit path; line 689, the batch path)

  The write tool's own call site was NOT reverted — it correctly records
  `record_write`, which is the whole difference between the two tools.

Hash before revert: 9ff4a6ae5d3a033cd2ed32a6ee52210a0811224f07623357ad3938e8282b7c9d
Restored and hash-verified identical afterwards (see "Restore" below).

Why this string is the defect, not an incidental failure
-------------------------------------------------------
The test reads 20 lines of a 200-line file, edits one of them, then attempts a
whole-file write. The test asserts that write is REFUSED. Under the reverted
code the write is ALLOWED and the harness reports success:

    Ok("overwrote book.txt (19 bytes)")

19 bytes is the length of the test's replacement text ("replaced all of it\n"),
so the harness reports a clean, successful, total overwrite of a 200-line file
on the strength of a 20-line read plus a one-line edit. The `.unwrap_err()` on
an `Ok` is the test's own refusal assertion firing — the model got the licence
it should never have been given.

That is the F01 guarantee defeated in three ordinary tool calls, with no large
file involved: the narrow read is the caller's own `limit`, not the byte cap.

Scope of this control
--------------------
It proves the behavioural test is discriminating for the route it names. It does
not prove the four other new unit tests discriminate; those were read and
labelled honestly in the milestone (three fail under the old code by
construction, two are over-refusal guards that pass under both by design).
