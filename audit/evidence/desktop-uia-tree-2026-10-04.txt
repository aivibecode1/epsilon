# The Epsilon window's accessibility tree, read through Windows UI Automation

Produced by `scripts/desktop-a11y-probe.ps1` on 2026-10-04. Reproduce with:

    pwsh -File scripts/desktop-a11y-probe.ps1 -Out audit/evidence/desktop-uia-tree-2026-10-04.txt

## What this is, and the layer it adds

Every accessibility claim in this repository stopped at *"egui emitted the node into the
AccessKit tree"*. Twenty-four desktop tests assert against a real `accesskit::TreeUpdate`,
but one read **inside the process that produced it**. Nothing had checked that the tree
reaches the **operating system's** accessibility API, which is the only thing a screen
reader actually talks to.

UIA is the Windows API NVDA and Narrator are built on. This is a client in **another
process** asking the OS for the window's descendants -- the same query a reader makes.
It is one full layer beyond anything the in-process tests can show: the tree crosses the
process boundary, the roles survive the translation, and the names arrive.

**It is not running a screen reader.** UIA returns the raw tree; a reader decides what to
*say* and in what order. The honest claim is "the platform exposes this", not "a reader
announced it".

**The window renders nothing and this still works.** No wgpu backend presents on this
machine, so the content area is blank -- accessibility is published by the application,
not by the compositor. That is why this probe succeeds where a screenshot cannot.
