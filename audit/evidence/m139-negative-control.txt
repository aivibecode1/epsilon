M139 NEGATIVE CONTROL — pi's third arm removed, the model reverts to nothing
==========================================================================

Defect under test
-----------------
`SessionStore::context_settings` ports pi's `getSessionContextSettings`
(`references/pi-0.85.1/packages/coding-agent/src/core/session-manager.ts:362-374`).
pi's loop has three arms:

    if      (entry.type === "thinking_level_change")  thinkingLevel = entry.thinkingLevel;
    else if (entry.type === "model_change")           model = { provider, modelId };
    else if (entry.type === "message" && role === "assistant")
                                                      model = { provider: model };

The third arm is the one a faithful-looking port omits. It is what lets a session that
never had a `model_change` entry — written by an older build, or simply never switched —
still report the model it actually ran.

The control
-----------
The `EntryKind::Message` arm in `context_settings` emptied:

                EntryKind::Message { .. } => {
                    // CONTROL (M139): pi's third arm removed
                }

Everything else is untouched: the walk still runs, `model_change` still sets the
model, thinking level still resolves, and the path is still the selected branch. The
only thing removed is the ability to recover a model from the transcript itself.

Reading the result
------------------
`left: None`. That is the original bug reproduced exactly, in the shape it takes in
production: a session that ran on `gpt-x` for its whole life, with no explicit switch
anywhere, comes back with **no model at all**, and the caller falls back to the launch
default. From the user's side the model silently reverts — not an error, not a message,
just a different model than the one they were using a moment ago. That is why this
defect can survive for a long time: the failure mode is a silent revert, which reads as
intended behaviour rather than as a failure.

Which tests did NOT fail, and why that is the point:

  - `the_last_model_change_on_the_path_wins` passes, because a session with an explicit
    `model_change` does not need the third arm. A control that broke everything would
    prove less: it could not distinguish "the port is faithful" from "the port is strict".
  - `the_settings_survive_a_close_and_reopen` passes for the same reason — it writes a
    `model_change`, not an assistant message.

So exactly one test fails, and it is the one that names the rule a `model_change`-only
implementation gets wrong. That is the difference between a control and a coincidence.

Restoration
-----------
The arm was restored:

                EntryKind::Message { message, .. } => {
                    // pi's third arm: `entry.type === "message" && role === "assistant"`.
                    if let Message::Assistant(a) = message {
                        model = Some((a.provider.clone(), a.model_id.clone()));
                    }
                }

    $ cargo test -p epsilon-session --test session_store -- \
        model_change assistant_message_alone path_with_no_model thinking_level settings_survive
    EXIT=0
    test result: ok. 8 passed; 0 failed; 0 ignored; 0 measured; 49 filtered out

(The 8 includes 3 pre-existing pi-fidelity tests whose names contain `model_change`.)

The final battery (`m139`) was run against these restored bytes.

What this control does NOT cover
--------------------------------
It exercises the reader only. Nothing here proves the CLI's resume path *consumes* the
result — that is the separate, end-to-end concern recorded in the milestone's "What
nothing exercises" section, and it is genuinely unexercised.
