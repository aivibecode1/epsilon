## What changed, and why this file exists

The 2026-10-04 dump (kept beside this one) contains **two `TreeItem`s named
`File · README.md`** -- one at the workspace root, one under `agents/`. Every file row was named
after its last path segment, so a screen reader arriving by rotor or by search got two identical
entries and no way to choose between them, while a sighted reader resolved the same two rows from
the indentation.

File rows are now named by their **workspace-relative path**. Measured on the same probe, on this
tree:

    32 tree rows, 32 distinct names

and the pair that collided now reads:

    TreeItem               File · README.md
    TreeItem               File · agents/memory/README.md

**This is the same evidence one layer out, not a new claim.** The in-process test
(`a_file_row_is_named_by_its_path_so_two_of_the_same_name_differ`) asserts on the AccessKit tree
this process produced; this file is the platform tree read by **another process**, which is the
only thing a screen reader talks to.

## Still open, unchanged by M312

**One unnamed `ScrollBar`**, and it is deliberately not a one-line fix: egui's
`Context::accesskit_node_builder` is *get-or-create*, so naming both axes unconditionally would
create two phantom nodes for a bar that is not shown. The probe exits 1 on any unnamed node and is
kept out of `gate.ps1` for that reason -- a gate that is red for a known finding gets deleted
rather than read.

## What this still is not

It is not a screen reader. UIA returns the raw tree; a reader decides what to *say* and in what
order. No reader has been run against this window.window: name=Epsilon type=Window class=Window Class
