| Its manifest name is `@deepseek-ai/dsh-desktop`, described as "Electron desktop shell for a bundled dsh runtime and external plugins" | `apps/desktop/package.json:2-3` |
| Version in this tree is `0.2.1-alpha.1`; package entry is `lib/main.js` | `apps/desktop/package.json:4`, `apps/desktop/package.json:8` |
| Licence: **MIT**, `Copyright (c) 2026 DeepSeek` | `LICENSE:1`, `LICENSE:3` |

| DeepSeek Harness is in developer preview and "THERE WILL BE COMPATIBILITY-BREAKING CHANGES" | `README.md:13` |

The repository root `README.md` describes `dsh` as an open-source agent harness by DeepSeek AI
built on an everything-is-a-plugin architecture powered by Cordis (`README.md:5-7`).

### 1.2 Technology determination — **Electron + Chromium-rendered web UI. Not Tauri, not native.**

Facts I can cite:

| Claim | Evidence |
|---|---|
| The desktop application process imports Electron's `app`, `BrowserWindow`, `Menu`, `dialog`, `ipcMain`, `session`, `shell`, `protocol`, `nativeTheme`, `powerMonitor` | `apps/desktop/src/main.ts:8-24` |
| `electron` is a dependency of the desktop package at `^44.0.0` | `apps/desktop/package.json:63` |
| `electron-builder` `^26.15.3`, `@electron/get`, `@electron/notarize` are its build tooling | `apps/desktop/package.json:56-63` |
| Its own README states the runtime: "dsh runs under Electron with `ELECTRON_RUN_AS_NODE=1` and `--expose-internals`" | `apps/desktop/README.md:76` |
| The renderer is a **web document**: a privileged custom scheme `dsh-app://` is registered | `apps/desktop/src/main.ts:132-142` |
| Electron serves the packaged Web bundle at `dsh-app://app/` and forwards everything else to the authenticated Host over HTTP | `apps/desktop/src/main.ts:662-677` |
| The window is created with `nodeIntegration: false`, `contextIsolation: true`, `sandbox: true` | `apps/desktop/src/main.ts:229-237` |
| The web UI itself is React: `react` / `react-dom` `^18.2.0` are devDependencies and the welcome entry is `.tsx` | `apps/desktop/package.json:74-77`, `apps/desktop/src/client/WelcomePage.tsx:1` |

**Not determined / explicitly ruled out:** there is no Tauri, `wry`, or `winit` reference in
`apps/desktop/package.json`; I searched the desktop manifest and found none. The renderer is not
declared to be any particular framework in `apps/desktop` itself — the React dependency there is
for the *welcome* document only (`apps/desktop/src/client/welcome.tsx`). The main product renderer's
framework is determined in §1.3.

### 1.3 Where the user-visible UI actually is — **not in `apps/desktop`, and not in `packages/web`**

This is the single most important finding for a port, and it contradicts the framing in the brief.

- `apps/desktop` contains the **shell**: window creation, application menu, tray, keyboard
  interception, updates, onboarding/welcome, crash recovery, the embedded Platform view, and
  three shell-owned HTML documents (`apps/desktop/renderer/welcome.html`,
  `apps/desktop/renderer/update-dialog.html`, `apps/desktop/renderer/mandatory-update.html`).
- `apps/web` is a **40-line Vite host**. Its whole entry is `apps/web/src/main.ts`; it imports
  `@deepseek-ai/dsh-client-web` and mounts `AppWebEntry` (`apps/web/src/main.ts:3`, `:20`).
- The product UI is defined in **62 shared client-UI workspace packages under
  `packages/client/ui-*`** plus `packages/client/web`, `packages/client/ui-renderer`,
  `packages/client/ui-primitives`, `packages/client/shortcuts`, `packages/client/locale`,
  `packages/client/store`, `packages/client/connection`, `packages/client/file-upload`.
- The reference's own `packages/client/AGENTS.md` calls this tree "the browser side of the dsh
  web GUI" plus "its build entry `apps/web`" — the *same* client that Desktop loads.

**`packages/web/` is not the UI.** The `web` package group contains the agent's *web tools*:
`packages/web/` = `tool-web`, `web`, `web-fetch-http`, `web-search-deepseek`,
`web-search-exa`, `web-search-perplexity`. The brief's guess that "the desktop's UI is defined in
`packages/web`" is **wrong**; the correct source is `packages/client/*`. This is recorded here so
the parity matrix is not built against the wrong tree.

**`apps/desktop-host/` is part of the desktop surface but is not a UI.** It is the private
Node-mode process: "Private Node-mode host process for the Electron desktop application"
(`apps/desktop-host/package.json:3`), whose entry is described as "Launch the Desktop profile
through the Web application and report its URL to Electron"
(`apps/desktop-host/src/index.ts:1`). It boots the same profile runner the Web app uses, with
`args: ['--no-open', '--port', '0']` so Desktop never collides with Web's `3080`
(`apps/desktop-host/src/index.ts:30`; `apps/desktop/README.md:7`).

### 1.4 What this means for parity

Epsilon's `epsilon-desktop` is a **native egui/eframe** application; DSH Desktop is an
**Electron + Chromium** application. The parity target therefore has to be **behavioural** —
windows shown, dialogs raised, lifecycle rules honoured — and *not* visual or implementation
parity. Every row below is written to be implementable without a webview: it names a screen, an
action, a limit, and a lifecycle rule.

### 3.2 Claims worth checking against the code

These are the statements in the README that a porter is most likely to accept uncritically:

1. **"An Electron shell around the complete dsh Web application"** (`README.md:7`) — confirmed by
   code: the shell serves the packaged `@deepseek-ai/dsh-web-frontend` dist at `dsh-app://app/`
   (`src/main.ts:667-669`) and `apps/web/src/main.ts:3,20` mounts the same entry. **Confirmed.**
2. **"Desktop does not enable scheduled tasks by default"** (`README.md:43`) — consistent with
   `packages/schedule` being an opt-in profile plugin; not verified from the desktop shell.
3. **"Account sign-in is not connected; the Sign in button is disabled"** (`README.md:468`) — the
   shell *does* build and execute a full browser sign-in flow (`src/main.ts:1153-1167`), so this
   limitation is about the shipped release's configuration, not about missing code. **Recorded as a
   claim that the code partially contradicts.**
4. **Update presentation claims a spinner with download percentage and a "persistent red retry
   action"** (`README.md:413`) — the shell side only supplies phase/version/percent/failure
   (`src/update-presentation.ts:44-51`); the control itself lives in the shared client UI, which is
   inventoried in §4.6.

### 3.3 What is missing

- **No Desktop user guide.** `docs/user/guide/` covers Web only.
- **No feature catalogue** for the shared client UI as a whole; behaviour is documented per
  subsystem page and per package README.
- The reference ships **no accessibility conformance statement** for either surface. No ARIA audit,
  no screen-reader walkthrough, no contrast table. Epsilon's AGENTS.md §8 sets WCAG 2.2 AA as a
  floor; the reference gives no citable baseline for it, so parity on accessibility must be
  measured against DSH's *implementation*, not against a DSH document.

## 7. How to use this file

Each row is written to be implementable in a native egui application: it names a **screen**, an
**action**, a **limit** or **default**, and a **lifecycle rule**. Where DSH's behaviour depends on
a platform (Windows/macOS/Linux), that is called out in `notes` rather than left implicit, because
a porter writing native code has no Electron to inherit the platform branch from.

### 7.2 The ten behaviours a porter would otherwise get wrong

1. **Enter grants, Escape denies in the approval panel** (`C`/`I-103`, D-072) — and the
   fail-closed rule lives in the **host**, not the card: no answerer ⇒ `unavailable` ⇒ deny
   (`I-107`, D-078).
2. **There is no "always allow" in the approval UI at all** (`I-102`, D-071). Persistent policy is
   a host concept. Adding the checkbox is a defect, not a feature.
3. **`Esc Esc` is a 500 ms *sequence*, not a chord**, and it is invalidated by approvals, iframes,
   terminals, `[inert]`, IME and any session/turn change (`C-140`, `S-118`, `P-136`).
4. **The default key bindings have six profiles, and `web:linux` is unbound for all 18 commands**
   (§4.2.1). Desktop and Web differ for nearly every command.
5. **Collapsed sidebar width is 0, not 56, on macOS and Windows** (`L-102`) — and the left
   column's width is forgotten on close while the right panel's is kept (`L-102`, `L-104`).
6. **The transcript default work-detail mode is `standard` on Desktop and `detailed` on Web**,
   chosen by the `'dshDesktop' in globalThis` marker rather than a platform API (`C-101`).
7. **The right panel is capped at two panes with 20 %–80 % divider ratios, and splitting has five
   distinct localized refusal reasons** (`L-162`), each keeping the control focusable.
8. **Every destructive schedule delete is confirmed with focus on Cancel — but the session-header
   popover's Delete is not confirmed at all** (`I-121` vs `I-122`). Faithful parity means shipping
   both; the goal strip's Clear has no confirmation either (`I-134`).
9. **Terminal output in a chat row is deliberately uncapped** while read/search/diff cards cap at
   8/8/9 lines (`C-123`, `C-124`, `C-127`, `C-135`).
10. **Closing the main window hides it, and the Host keeps running** (`D-023`); the quit decision
    is made by asking the Host what it would interrupt, and an unknown answer is treated as
    "tasks running" (`D-031`, `D-032`) — never as a silent quit.
