# G3/G4 — Checkpoint restore and session repair: what the code does, and the design that fixes it

Audit of ledger entries F07, F08 and F15 (`audit/02-defect-ledger.md`), judged only from code. Baseline: `git log -1` = `6f3d544` (2026-09-20), plus uncommitted work in `crates/epsilon-session/src/store.rs` and `crates/epsilon-ext/src/host.rs`. No source file was modified and no cargo command was run (a build owns this machine), so every claim below comes from reading the working tree; none of it is backed by a test run I performed.

The ledger was last written at `5ab723f` (2026-09-18; `git log -- audit/02-defect-ledger.md`). Two commits landed afterwards that rewrite the file F15 describes: `46235bb` ("fix(m100): a revert that cannot restore a file must not delete it") and `d4d70ff` ("fix(m104): a checkpoint restore verifies the file before overwriting it"). That provenance matters: **F15's cited lines no longer exist in that form**, so the entry is stale rather than merely disputable.

Two different "restores" live here, and G3/G4's text blurs them. One puts **file contents** back before a tool write (`CheckpointStore`, `crates/epsilon-tools/`); the other puts a **transcript** back from a session file (`SessionStore`, `crates/epsilon-session/`). They share only vocabulary.

## 1. What the code does today

### 1.1 The workspace checkpoint store

`CheckpointStore::record` runs once per file per call, before the first byte changes — for `write` at `crates/epsilon-tools/src/files.rs:358-360` and for `edit` at `:534-536`. Both call sites **discard the return value**: `CheckpointStore::open(&workspace).record(&workspace, &path, "write");` (`files.rs:359-360`) and the same one-liner for `"edit"` (`files.rs:536`).

`record` (`crates/epsilon-tools/src/checkpoint.rs:160-268`) has four outcomes. The file did not exist → `blob: None, existed: false`, `Recorded::Created` (`:160-178`). It exceeds `MAX_FILE_BYTES` (2 MiB, `:38`) → `blob: None, existed: true, skipped: Some(reason)`, `Recorded::Skipped(reason)` (`:186-211`). An I/O or ledger failure → `Skipped` too (`:182`, `:215`, `:221`, `:224`, `:241-249`). Otherwise the bytes land in a content-addressed blob and `Stored` comes back (`:217-254`). The ledger append is fallible and no longer swallowed — `append` returns `Result<(), String>` (`:268-284`), and a failed append after a successful blob write reports `"captured {blob} but the ledger could not be written: {e}"` (`:246-248`).

A restore is `CheckpointStore::restore` (`checkpoint.rs:322-352`), traced step by step. It resolves the stored workspace-relative path to a target (`:323`). A `None` blob with `existed: true` refuses, naming the recorded skip reason (`:324-335`). A `None` blob with `existed: false` removes the target and reports 0 bytes (`:336-339`). Otherwise it reads the blob (`:341-342`), calls `check_unchanged` (`:346`), and writes (`:347-351`); `check_unchanged` (`:416-454`) compares the file's current content hash against `entry.digest` and refuses on a mismatch, and an entry with no digest (one that predates content verification) is refused too (`:423-441`). The decisive lines are the guard and its doc comment: `let Some(blob) = &entry.blob else { if entry.existed { … return Err("cannot restore {}: nothing was captured for it ({why}). The file is untouched rather than removed — revert it by hand.") } }` (`checkpoint.rs:324-334`).

**`restore` has no production caller.** Grepping `\.restore\(|store\.record|CheckpointStore::open` across `crates/` returns the two `record` sites in `files.rs` and otherwise only `#[cfg(test)] mod tests` in `checkpoint.rs` (`:494-751`). There is no `/undo`, `/rollback` or `/restore` in `crates/epsilon-tui/src/picker.rs:253-410` and no checkpoint verb in `crates/epsilon-cli/src/main.rs`; `crates/epsilon-tui/src/undo.rs` is editor-buffer undo. The ledger's own hedge — "No normal UI route to this API was established" (`audit/02-defect-ledger.md:255`) — is still exactly right.

### 1.2 The session-file repair path (F08's subject)

Opening a store (`crates/epsilon-session/src/store.rs:271-347`) takes the write lease, opens the file read+append, reindexes, and physically truncates when the scan reports a torn tail: `if !store.reindex()? { store.truncate_to_index()?; }` (`store.rs:338-339`).

`reindex` (`:469-631`) splits the file into non-blank lines with byte offsets (`:488-495`), consumes a leading header line into `self.header` and records its end offset (`:498-505`, uncommitted), then classifies the rest. A typed parse failure falls through to a lenient parse (`:544`); when that also fails and the line is the **last** one, it becomes a torn tail — `torn_tail = true` at `:557-558` (unparseable last line) and `:568-570` (untyped last line) — while the same failure anywhere else becomes `first_bad` and the open fails with `StoreError::Corrupt` (`:578-579`). A second header line follows the same rule: torn when last (`:533-534`), corruption mid-file (`:535-536`). `reindex` returns `Ok(!torn_tail)` (`:631`): **one boolean, and that boolean is the entire diagnosis a torn tail gets.** The `diagnose_line` reason (`:1248-1271`) is computed only on the corruption path.

`truncate_to_index` (`:645-655`) cuts the file to `keep_end()`, which is now "past the last indexed entry, else past the header, else 0": `self.index.last().map(|loc| loc.offset + loc.len as u64).or(self.header_end).unwrap_or(0)` (`store.rs:633-639`, uncommitted).

That uncommitted work fixes a **committed** defect. At `HEAD`, `truncate_to_index` computed `self.index.last()…unwrap_or(0)` inline, so a header plus a torn first entry (no indexed entry at all) was cut to zero bytes while `self.header` still answered `Some`; the next append then skipped the header it believed existed, and the file reopened as a headerless v1 session — new id, no cwd, no parent — silently `migrated` at the next open (the header-stamp condition is `store.rs:341-346`). The same working-tree change renames `migrated_entries` to `cached_entries`, populates it for every file, and makes `pop_last` shorten it in step with the index (`:789-826`); at `HEAD` a popped entry stayed in that read-through cache, so the next append's entry was served from the stale copy under its own sequence number. I did not run the new tests (`crates/epsilon-session/tests/session_store.rs:1582`, `:1683`); I read them, and they pin those two properties.

The other consumers add no state the store lacks. `repair_on_open` (`crates/epsilon-session/src/repair.rs:92-167`) reads the active branch and appends synthetic tool results plus a `TurnEnd{Aborted}`, returning `RepairReport` with typed `RepairKind`s (`:25-86`). The CLI resume path treats its failure as advisory and continues — `Err(e) => eprintln!("repair warning (continuing): {e}")` (`crates/epsilon-cli/src/main.rs:1702`) — while the TUI's `Agent::live_resume` propagates it instead (`crates/epsilon-core/src/lib.rs:812`).

### 1.3 The durable-commit path (F07's subject)

Every transcript message goes through one private function that throws its result away: `fn persist(&self, m: &Message)` (`core/src/lib.rs:983`) locks the store and then `let _ = st.append(EntryKind::Message { … });` (`:987`). `pop_last_message` (`:995-1005`) does the same with `s.pop_last()` (`:1003`), after mutating runtime history (`:996-998`). `Agent::store()` (`:939-941`) is a no-op when no store is attached — `--tui` without a session file, or a `task` child before its store exists — where "no failure" and "nothing durable" are the same path. Provider requests read the **store's** projection when one is attached (`try_context_view`, `:1139-1154`), which is what makes a divergence a correctness problem rather than a display one. The **compaction** commit was fixed: it appends first and refuses to advance on failure (`:2022-2037`, `CompactionOutcome::Failed`), rolling the entry back when the in-memory replace cannot happen (`:2039-2052`). The overflow-retry discard (`:1425-1432`) still calls `pop_last_message`, so it inherits the silent path.

## 2. Each ledger entry, judged

### F15 — "Checkpoint restore conflates skipped with deleted": **wrong at this commit; the surviving defect is the discarded outcome, not the conflation**

Every clause of the entry's evidence (`audit/02-defect-ledger.md:253`) is refuted by the file it cites. "`restore()` treats every `None` blob as deletion (`:261-277`), without checking skip/existence" — false: `restore` branches on `entry.existed` at `crates/epsilon-tools/src/checkpoint.rs:325` and refuses at `:330-334`. "Ledger append errors are swallowed (`:223-235`) while capture can report success (`:211-216`)" — false: `append` returns `Result<(), String>` (`:268-284`), and both the oversized path (`:205-210`) and the stored path (`:241-249`) turn an append failure into `Recorded::Skipped`. "Restore writes without checking later user changes (`:265-270`)" — false: `check_unchanged` at `:346` and `:416-454`. `audit/07-inconsistencies.md:21` cites the same dead lines, and `docs/history.md:133` records M100 as landed with both halves pinned by tests.

What is **still true** is narrower, and it is why F15 should stay open. First, the state is still field combinations rather than a type: "created" (`blob: None, existed: false`), "skipped" (`blob: None, existed: true, skipped: Some`), "captured" (`blob: Some, digest: Some`) and "captured by an older build" (`blob: Some, digest: None`) are four cases spread over two `Option` fields and a `bool` (`checkpoint.rs:42-73`). Second, and this is the live one, the outcome the capture path already computes is thrown away at both call sites (`files.rs:359-360`, `:536`): the harness knows a file was too large to checkpoint and tells nobody, so the user learns it only if and when a restore API is exposed. The acceptance list asked for a preview and a human override (`audit/02-defect-ledger.md:257`); neither exists, and neither does any caller.

### F07 — "Persistence failures are discarded while model/store views diverge": **confirmed** (line citations stale, compaction clause out of date)

The live evidence is `persist`'s `let _ = st.append(…)` at `crates/epsilon-core/src/lib.rs:987`, `pop_last_message`'s `let _ = s.pop_last()` at `:1003`, the store-preferred context view at `:1139-1154`, and the resume path that sets the loss radius (`crates/epsilon-cli/src/main.rs:1682-1712`). The entry's line numbers (`:743-777`, `:1497-1512`, `:1592-1604`) have all shifted. Its compaction clause is **out of date**: compaction now refuses to advance when the durable append fails (`:2022-2037`). Two aggravations the entry does not mention, both cited above: with no store attached the failure is silently absent rather than silently ignored (`:939-941`), and a partial `write_all` inside `append` (`crates/epsilon-session/src/store.rs:704-706`) leaves a fragment past the index that the *next* open classifies as a torn tail and deletes — so a failed append also pre-authorizes deletion of the bytes it half-wrote.

### F08 — "Unsupported final entries are truncated": **partly true; the header clause is stale, the rest stands**

*True:* a complete, well-formed final line whose `kind.type` this build does not know is indistinguishable at reindex time from a half-written one. `parse_entry_lenient` returns `None` for it (`store.rs:1273-1287`, because `serde_json::from_str::<SessionEntry>` fails and `is_legacy_entry_shape` is false, `:1291-1307`), and the last-line branch sets `torn_tail = true` without ever calling `diagnose_line` (`:556-564`); `open` then truncates it (`:338-339`). The repository's own test names this as intended behaviour — `a_torn_tail_is_still_tolerated_whatever_its_shape` (`crates/epsilon-session/tests/session_store.rs:739-755`) loops over a cut line and a complete `{"kind":{"type":"future_thing"}}` line and requires both to open cleanly. The acceptance criterion ("unknown complete final entry … refused with the entire file unchanged", `audit/02-defect-ledger.md:149`) is therefore unmet, and the test codifies the opposite, as `audit/evidence/integration-core-review.json:219` already recorded.

*Partly stale:* "a header plus a torn first entry leaves no indexed entry, so repair also deletes the header" (`:147`) is true at `HEAD` and fixed by the uncommitted `keep_end` work (`store.rs:633-639`, `:645-655`, test at `session_store.rs:1582`). The rest holds as written: only the last line may be torn, a mid-file bad line is refused with the file untouched (`:578-579`, tests at `session_store.rs:449-502`), and a clean header-only file is never subject to this repair because it never sets `torn_tail`.

## 3. The concrete failures

**F15-a — a skipped capture is invisible, so the undo the user believes in does not exist.** The model writes `src/big.bin` (3 MiB); `record` writes a ledger line with `skipped: Some("3145728 bytes is over the 2097152-byte checkpoint limit")` (`checkpoint.rs:186-211`); `files.rs:359` discards `Skipped(reason)`; the tool reports `overwrote src/big.bin (3145728 bytes)` (`files.rs:369-376`); the user asks to undo; the restore refuses (`checkpoint.rs:330-334`) or cannot be attempted at all. The file survives, so the loss is information and time — recovery means a git checkout, an editor history, or re-deriving the content. The failure to guard against is the silence, and the silence is at `files.rs:359-360`, not in the store.

**F15-b — the store cannot say what happened, so no future caller can either.** `restore` reports `Result<u64, String>` (`checkpoint.rs:322`). "Restored 4096 bytes", "removed a file the agent created" (also `Ok(0)`), "no capture exists for this path", and "the capture was skipped" all collapse into two channels, one of them an untyped string. A UI that wants a truthful per-file summary — Hermes prints exactly that (`references/hermes-agent-2026.9.14/tools/checkpoint_manager.py:765-776`: `restored_files`, `skipped_user_edits`, `skipped_oversize`, `failed_deletes`) — has nothing to read.

**F07-a — the transcript forks, then loses the turn.** With a store attached, the user prompts; `push_message` writes memory and calls `persist`, whose `append` fails (disk full, permissions, a half-written line) and whose error is dropped (`core/lib.rs:987`); the run continues and every later request is built from the **store** projection (`:1139-1154`), so the model answers a transcript that does not contain the prompt. The user quits and resumes; `open` reindexes and truncates any fragment (`store.rs:338-339`), and the resume prints `resumed N entries` for a transcript missing that turn (`crates/epsilon-cli/src/main.rs:1704-1712`). Nothing in the loop notices. The user loses a turn they paid for and the guarantee that a resumed session is the session they had.

**F07-b — the repair warning is advisory.** A session file has a bad last line; the user runs `--resume`; `repair_on_open` fails after `open` has already truncated the tail; the CLI prints `repair warning (continuing)` (`main.rs:1702`) and resumes from whatever survived. The transcript is shorter than the file was, and the only signal is one stderr line in a path the user may not read.

**F08-a — a session from a newer build is deleted by an older one.** A session's last line is a complete entry with `kind.type = "future_thing"`; the user opens it with this build; `reindex` marks it torn (`store.rs:556-564`), `open` truncates it (`:338-339`), and the entry is gone with no error, no report and no backup. Running one build ahead on another machine silently costs the last turn of that session — and the diagnosis that would have said so already exists (`LineDiagnosis::UnknownEntryType`, `:57-60`, whose own doc says refusing beats dropping).

## 4. The design

Adopt a typed tri-state at each seam, because both failures here are "two different situations encoded in one value". The codebase already believes this — `Recorded` separates stored/created/skipped (`checkpoint.rs:76-89`), `LineDiagnosis` exists to keep "damaged" apart from "written by something newer" (`store.rs:42-65`), and `RepairKind` exists so a caller reports a kind rather than a count (`repair.rs:18-55`). The fix carries those distinctions one level further, to the values callers see.

**4.1 Restore becomes explicit about the third state.** In `crates/epsilon-tools/src/checkpoint.rs`, `Recorded` (`:76-89`) keeps its role as the capture-side vocabulary, and the restore side gains a mirror:

- `pub enum RestoreOutcome { Restored { path: String, bytes: u64 }, Removed { path: String }, Absent { path: String }, Skipped { path: String, reason: String } }`
- `pub struct Captured { pub path: String, pub outcome: Recorded }` — what `record` returns, so the caller knows *which* file the outcome belongs to instead of reconstructing it.
- `pub fn restore(&self, workspace: &Path, entry: &Entry) -> Result<RestoreOutcome, String>` and `pub fn restore_path(&self, workspace: &Path, path: &str) -> Result<RestoreOutcome, String>`, where `restore_path` looks up `latest_for(path)` and answers `Absent` when there is no entry. `Absent` is the state whose absence caused this bug class: with only `Ok`/`Err`, "we have no checkpoint for this file" must be told either as a success (a lie) or as an error string that reads like damage.
- `Unreadable` needs no variant *for the caller*: a missing blob or failed read (`:341-342`) is a genuine error and stays `Err(String)`, because there is no partial action to report. It is still distinguishable from `Skipped` by construction — `Skipped` never touches the filesystem. I considered a fourth variant and rejected it: `restore` either acted (Restored/Removed), deliberately did not (Absent/Skipped, both non-errors, both carrying a reason the caller must show), or failed (Err). That is the whole space.

Why this shape rather than a patch: an `if entry.skipped.is_some()` check at each call site fixes today's caller and re-breaks the next one, because the information would remain an `Option` field a caller can ignore. A return type the caller must `match` makes "I did not restore this" impossible to swallow.

**4.2 Captures stop being silent.** At `files.rs:359-360` and `:534-536`, bind the result and append one sentence to the tool output when it is not `Stored`: a skipped capture prints `no undo checkpoint for <path>: <reason>`; `Created` prints nothing (it is the normal case). This follows the read tool's own rule that a partial view is reported, not hidden — the `read` result carries a `truncated_by` field the model sees (`crates/epsilon-tools/tests/builtin_tools.rs:452`) — and the incompleteness-notice pattern in `crates/epsilon-core/src/untrusted.rs:19-32`. It must not become a `ToolFailure`: the edit succeeded and must still report success (`checkpoint.rs:144-146`).

**4.3 The restore becomes reviewed and caller-driven.** Expose `preview_path(&self, path) -> Result<Preview, String>` returning the entry, what its `tool`/`at` fields say, and what `check_unchanged` currently answers; run the actual `restore` **inside** `crate::mutation::with_file_mutation_queue` for the same path the write and edit tools use (`crates/epsilon-tools/src/mutation.rs:31-39`). Today the digest check and the write are not serialized against a concurrent tool write (`checkpoint.rs:346-351`) — a narrow but real window, and the queue is the existing answer.

**4.4 The session store gains a diagnosis for a refused tail.** `reindex` already computes `diagnose_line` for non-final bad lines (`store.rs:562`, `:572`) and discards it for final ones. Record `tail: Option<LineDiagnosis>` and return a small typed report instead of `bool` (`:631`), so `open` can choose: a `NotJson` tail (a genuine partial write) is truncated and reported as today; an `UnknownEntryType` or `SecondHeader` tail is **refused**, leaving the file byte-identical, exactly as the mid-file path already does (`:578-579`). Keep a thin `Result<bool>` wrapper if other callers need it — I enumerated only `open` (`:338`), `persist_migration` (`:401`) and the test at `session_store.rs:302`, all in-tree.

**4.5 F07's commit rule, and what the UI says.** Give the store one explicit answer to "what does the loop do when the durable append fails", and make it the same answer everywhere: `Agent::persist` returns `Result<(), StoreError>` and `push_message` propagates it into the run, which stops at a defined boundary and emits a `Notice` naming the cause — or the agent detaches the store and announces in-memory-only mode. Either is defensible; preferring one source for the model and another for the user is not, and that is what `persist` does now (`:987`). With 4.1-4.3 in place a frontend can be honest in four sentences: `restored <path> (<bytes> bytes, back to the state before the <tool> at <time>)`; `removed <path> (the agent created it — reverting the creation)`; `<path>: no checkpoint was recorded, so there is nothing to undo`; `<path>: not restored — <reason> (the file is unchanged)`; plus, for the refusal, `<path> changed since the snapshot; restoring would discard that work — read it first`. The preview must show the same sentence the action will print afterwards. No product surface does this yet, and the UI half is where the ledger's "blocker before exposure" language (`audit/02-defect-ledger.md:255`) applies.

## 5. Tests to add

Checkpoint store (`crates/epsilon-tools/src/checkpoint.rs`, `mod tests`):

1. `restoring_a_skipped_capture_reports_skipped_and_leaves_the_file` — record an oversized file, then `restore`; assert `matches!(outcome, Ok(RestoreOutcome::Skipped { .. }))`, that the reason contains "limit", and that the bytes on disk are the original ones. The existing test (`:653`) pins the error form, this pins the typed one; delete the `entry.existed` branch at `:325` and it must fail with the file gone.
2. `restoring_a_path_with_no_entry_reports_absent` — nothing recorded: `restore_path` returns `Absent` and the target is untouched; map `Absent` onto `Restored { bytes: 0 }` and it must fail.
3. `restoring_an_entry_whose_blob_is_gone_is_an_error_not_a_skip` — record, delete the blob from `.epsilon/checkpoints/blobs/`: assert `Err` naming the blob, the target unchanged, and specifically that the outcome is *not* `Skipped`.
4. `a_skipped_capture_is_reported_in_the_write_tools_output` (in `crates/epsilon-tools/tests/`) — run the real `write` tool against an oversized file and assert its output contains `no undo checkpoint` and `limit`; restore the `let _ =` at `files.rs:359` and it must fail.
5. `eviction_reports_the_capture_it_dropped` — with `with_max_bytes` small enough to evict, `evict_if_needed` (`checkpoint.rs:371-401`) must name the removed blob, and restoring an evicted entry must be an error naming it, never a silent removal.

Session store (`crates/epsilon-session/tests/session_store.rs`):

6. `a_torn_first_entry_does_not_take_the_header_with_it` — already in the working tree (`:1582`); the assertions that matter are `store.header().unwrap().id == "ses_keepme"` and one surviving line on disk after `open`.
7. `popping_the_last_entry_keeps_the_header_and_the_read_cache_in_step` — also in the working tree (`:1683`); asserts `read_all` returns `["first", "third"]` after pop + append.
8. `a_complete_unknown_final_entry_is_refused_not_truncated` — a session whose last line is the complete `{"kind":{"type":"future_thing"}}` entry must make `open` return `Err(StoreError::Corrupt { line, diagnosis: LineDiagnosis::UnknownEntryType { .. } })` **and** leave `std::fs::read` of the file equal to the bytes written; with the tri-state reverted the file opens and the last line is gone.
9. `an_unterminated_final_line_is_still_repaired` — the same file cut mid-JSON on the last line must still open, fragment gone, header and earlier entries intact: the pair that keeps (8) from turning "repair is expected" into "repair never happens".
10. Amend `a_torn_tail_is_still_tolerated_whatever_its_shape` (`:739-755`): keep the cut-line half, move the complete-unknown-type half to (8) and assert refusal there — the one existing test the ledger asks to amend (`audit/02-defect-ledger.md:149`).

Core loop (F07) needs one seam first: a private `#[cfg(test)] fault: Option<StoreFault>` on `SessionStore`, consulted in `append`/`pop_last` before the write, because injecting a real I/O error portably is otherwise a permissions trick I have not verified on this machine.

11. `a_failed_durable_append_stops_the_run_and_says_so` — arm the fault for the assistant message, run one faux turn, assert no further provider request (count `FauxProvider` calls), that the outcome carries the store error, and that an `AgentEvent::Notice` names it.
12. `a_failed_durable_append_never_leaves_the_views_apart` — afterwards the store's `model_view()` and `Agent::history()` must agree on how many messages exist; that is what F07's acceptance needs (`audit/02-defect-ledger.md:141`), and anything weaker passes today.
13. `the_overflow_discard_reports_a_failed_pop` — arm the fault for `pop_last`, drive the overflow-retry branch (`crates/epsilon-core/src/lib.rs:1417-1448`), and assert the retry does **not** proceed on a store that still contains the discarded message.
