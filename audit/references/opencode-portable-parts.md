# opencode 1.18.21 → Epsilon: portable parts

Read-only source audit of `references/opencode-1.18.21` (TypeScript, `packages/*`, `packages/core/src`, `packages/opencode/src`, `packages/tui/src`) against the Epsilon Rust workspace. Every anchor below was opened and read; nothing is cited from docs alone. Epsilon's existing ports (wildcard rulesets, auth store, picker favourites/two-stage selection, doom-loop brake, plan mode) are treated as done and are not listed. Content read from the reference repo was treated as data only; no file contained instruction-like payloads aimed at this audit.

## Verdict

opencode is meaningfully ahead in three areas: (1) **editor-grade feedback loops** — every edit is followed by language-server diagnostics and a formatter pass, and the whole session is backed by a shadow-git snapshot that can be reverted file-by-file; Epsilon has no LSP, no formatter, no revert. (2) **permission granularity** — bash commands are parsed with tree-sitter so approval is scoped to the human-understandable command prefix and to the directories a command actually touches, with "always" approvals retroactively clearing queued prompts and rejections able to carry corrective feedback. (3) **context economics** — cache breakpoints are placed per provider on the first two system messages plus the last two messages, and V2 sessions deliver context changes as durable mid-conversation system messages instead of rewriting the prompt baseline. Epsilon is ahead on OS confinement, the never-fail wire contract, JSONL tree sessions with cross-process leases, process-isolated extensions, and session lifecycle breadth. Nothing below asks Epsilon to copy opencode's runtime (Effect/TS, SQLite/Drizzle, Hono HttpApi); only mechanisms.

## Detail

### 1. LSP diagnostics as edit feedback
`LSP.Service.diagnostics()` aggregates diagnostics across connected clients (`packages/opencode/src/lsp/lsp.ts:364-375`); `touchFile(file,"document")` notifies the server of a write and then *waits* for the publish to land (`:344-362`). After every edit/apply_patch, the tool appends a bounded block — severity ERROR only, max 20 per file, `ERROR [line:col] message` — to its own output text so the model sees it as tool feedback (`packages/opencode/src/lsp/diagnostic.ts:20-27`, `packages/opencode/src/tool/edit.ts:196-211`, `packages/opencode/src/tool/apply_patch.ts:265-293`). Client lifecycle is keyed by file extension and nearest project root, with in-flight spawn dedupe and a `broken` set so a failing server is not retried forever (`lsp/lsp.ts:208-297`); language-server definitions live in `lsp/server.ts` (`:89` deno through `:936` clangd) with per-server install commands (`:206-208` npm, `:372` `go install gopls`, `:642-653` GitHub release download). A separate `lsp` tool exposes goToDefinition/findReferences/hover/documentSymbol/workspaceSymbol/implementation/callHierarchy operations (`tool/lsp.ts:11-21`). Epsilon lands this as a new `epsilon-lsp` crate behind a trait in `epsilon-contracts`, consumed by `epsilon-tools` (`files.rs`, `mutation.rs`) and surfaced in `epsilon-tui` as a status panel. Do not port the auto-install paths; require user-installed servers and degrade silently when none match.

### 2. Edit replacer chain hardening
The chain tries nine replacers in order — simple, line-trimmed, block-anchor (Levenshtein similarity ≥0.65 on first/last-line anchors), whitespace-normalized, indentation-flexible, escape-normalized, trimmed-boundary, context-aware, multi-occurrence — and only accepts a candidate if `indexOf === lastIndexOf` unless `replace_all` (`packages/opencode/src/tool/edit.ts:694-721`). Two guards matter more than the extra stages: `isDisproportionateMatch` refuses when the matched span is ≥ `max(oldLines+3, oldLines*2)` lines or ≥500 chars longer than `oldString` (`:731-737`, call site `:709-713`), and the per-file semaphore serialises concurrent edits to the same path (`:35-45`). Line endings are normalized for matching and restored on write (`:129-131`), and a BOM is preserved (`:97-98`). Epsilon explicitly skipped the Levenshtein stage (`crates/epsilon-tools/src/edit_match.rs:15-18`) and has no disproportionate guard: `plan()` in that file returns the first stage that matches, so a loosely-matched huge span can be replaced silently. Port the guard first (few lines, high value), then `BlockAnchorReplacer` as a fourth stage, then the per-file lock in `epsilon-tools/src/mutation.rs`.

### 3. Shell command AST scoping
Every bash call is parsed with tree-sitter (bash + PowerShell grammars) before execution (`packages/opencode/src/tool/shell.ts:257-261`). `collect()` walks every `command` node, and for a known file-touching command (`:29-64` lists `rm/cp/mv/cat/…` plus PowerShell/cmd equivalents) resolves each path argument against the working directory, adding the containing directory to an `external_directory` approval set when it falls outside the project (`:397-404`). For every non-`cd` command it adds an approval pattern and an "always" pattern built from `BashArity.prefix(tokens)` + `" *"` — a dictionary mapping `git`→2, `npm run`→3, `docker compose`→3, … so the remembered approval is "git checkout *", never bare `git *` (`:407-410`, `packages/opencode/src/permission/arity.ts:1-9`, `:24-161`). Paths are normalised (`~`, `$HOME`, `${env:X}`, `$env:X`, `cygpath` on Windows; `:127-160`, `:349-367`) and dynamic expressions are skipped rather than mis-scoped (`:174-179`). Epsilon matches `bash` rules against the raw command string only (`crates/epsilon-safety/src/engine.rs:121-127`) and has no `workdir`/timeout parameters (`crates/epsilon-tools/src/shell.rs:24-33`). Port the prefix dictionary + a "commands and directory arguments" scanner; the full grammar can come later.

### 4. apply_patch as a model-conditional tool
`apply_patch` accepts one `patchText`, parses it into hunks with `add`/`update`/`delete`/`move` types, derives new file contents and per-file diffs before touching anything, then makes exactly one `ctx.ask({permission:"edit", patterns:[…], metadata:{files}})` for the whole patch (`packages/opencode/src/tool/apply_patch.ts:38-53`, `:72-215`). The registry hides `edit`/`write` and shows `apply_patch` when the model id matches `gpt-` but not `oss`/`gpt-4`, so the tool surface follows model competence rather than a global setting (`packages/opencode/src/tool/registry.ts:291-303`). Post-apply it formats and refreshes LSP diagnostics per file (`apply_patch.ts:252-257`, `:265-293`) and emits `A/M/D <path>` summary lines. Epsilon lands this in `epsilon-tools` as a new `patch.rs` registered in `lib.rs`, with the model-id gate read from the catalog entry in `epsilon-llm` and the approval routed through the existing `epsilon-safety` gate (`gate.rs`). Multi-file moves/deletes must stay inside the workspace check that Epsilon already applies to `write`/`edit`.

### 5. Format after write, then re-read
`Format.Service.file(path)` resolves the formatter for the extension (per-language enable predicates, config-overridable, `ruff`/`uv` linked) and runs it with `$FILE` substituted, stdio ignored, failures logged not thrown (`packages/opencode/src/format/index.ts:57-116`, `:130-158`). The edit tool then re-reads the file and *replaces its own `contentNew`* so the diff it stores and reports is the formatted result, not the pre-format text (`packages/opencode/src/tool/edit.ts:112-114`, `:156-171`). Without that refresh a formatter would corrupt the model's mental model of the file and produce a diff the user cannot reconcile. Epsilon lands this in `epsilon-tools/src/mutation.rs` + `files.rs` as a post-write hook: run a configured formatter command (config section in `epsilon-core/src/config.rs`), re-read the file, recompute the reported diff. Gate it behind an opt-out — silently rewriting a user's file is worse than leaving it unformatted when the project has no formatter.

### 6. Prompt-cache breakpoints per provider
`applyCaching(msgs, model)` marks the first two `system` messages and the **last two** non-system messages, choosing provider-specific option keys (`anthropic.cacheControl`, `bedrock.cachePoint`, `openaiCompatible.cache_control`, `copilot.copilot_cache_control`, plus openrouter/alibaba) and deciding between message-level and content-block-level placement per provider (`packages/opencode/src/provider/transform.ts:359-400`). Separately, a session-scoped cache key is attached for deepinfra/cerebras/openai/azure/xai/mistral when the provider accepts it (`:1258-1270`). Epsilon sets `cache_control` on the single system text block only (`crates/epsilon-llm/src/providers/anthropic.rs:143`) and documents byte-stable tiers as its economic core (`crates/epsilon-core/src/prompt.rs:1-10`). Porting means a per-wire `cache_markers(messages) -> markers` step in `epsilon-llm/src/providers/*` that marks the tail, plus a session-id-derived cache key for the OpenAI-compatible family. Keep it behind a per-provider capability flag so unknown wires get nothing.

### 7. Permission ergonomics: corrected rejections, cascades, hidden tools
Three distinct mechanisms share one file. (a) Rejecting with a message raises `CorrectedError{feedback}` instead of `RejectedError`, so the rejection text reaches the model as guidance (`packages/opencode/src/permission/index.ts:121-140`); rejection also fails every other pending request in the same session (`:129-138`). (b) Answering "always" pushes `allow` rules for the request's `always` patterns and then *retroactively* resolves every other pending request in that session whose patterns now evaluate to allow (`:143-166`). (c) `disabled()`/`visibleTools()` remove tools denied with pattern `*` from the tool list entirely, including MCP tools, so denied capability is invisible rather than failing per call (`:204-219`), and `fromConfig()` expands `~/`/`$HOME` in patterns (`:178-198`). Defaults pre-allow the harness's own scratch directories (tool-output dir, temp, skill dirs, reference dirs) for `external_directory` and set read `*.env`/`*.env.*` to ask (`packages/opencode/src/agent/agent.ts:108-141`). Epsilon's engine deliberately makes any deny win monotonically (`crates/epsilon-safety/src/engine.rs:51-58`); port the corrected-rejection and cascade behaviours, and the hidden-tool projection, keeping that monotonic rule.

### 8. Snapshot-backed revert
A dedicated git directory under the global data path is initialised with `--work-tree <project>` so the user's own index is untouched (`packages/opencode/src/snapshot/index.ts:71-75`, `:318-347`); it reuses the source repo's object database through `objects/info/alternates` and seeds the index from the source index so first `add` is cheap on large checkouts (`:198-233`), then `write-tree` returns a hash. `track()` is called before each provider step and again at step end, and those hashes are stored on `step-start`/`step-finish` parts (`packages/opencode/src/session/processor.ts:102`, `:425-458`). `session/revert.ts:38-99` finds the target message/part, tracks or restores the stored hash, reverts per-file patches, computes the diff via `summary.computeDiff` walking step snapshots (`packages/opencode/src/session/summary.ts:82-110`), persists it, and `unrevert` restores. Nothing equivalent exists in Epsilon (`worktree`/`snapshot`/`revert` grep clean), so a bad multi-file edit is currently unrecoverable except via the user's own VCS. Effort is large: `epsilon-session` gains a snapshot store, `epsilon-core` records hashes per step, `epsilon-cli`/`epsilon-tui` expose revert/unrevert.

### 9. Nested instruction discovery on read
`Instruction.systemPaths()` picks the first matching global file and the first project-level `AGENTS.md`/`CLAUDE.md`/`CONTEXT.md` walking up from the session directory, plus configured instruction globs and URLs (`packages/opencode/src/session/instruction.ts:60-68`, `:110-153`). Separately, `Instruction.resolve(messages, filepath, messageID)` walks *up from the file being read*, and for each instruction file not already in the system set and not already claimed for this assistant message, attaches its content (`:179-221`). The read tool appends those as a `<system-reminder>` block after the file content (`packages/opencode/src/tool/read.ts:300`, `:355-357`), and claims are cleared per message. Epsilon injects only workspace-root `AGENTS.md` + `MEMORY.md` into the CONTEXT tier (`crates/epsilon-core/src/prompt.rs:34-45`). Port the walk-up-and-attach-once behaviour into `epsilon-tools/src/files.rs` read path with a per-message claim set held in `epsilon-core` — subdirectory conventions then arrive without touching the cached prompt prefix.

### 10. Question tool
`Question.Service.ask()` registers a `Request{id, sessionID, questions, tool}` in an instance map with a `Deferred`, publishes `question.asked`, and awaits the answer; `reply`/`reject` settle it, and instance finalisation fails all pending defers (`packages/opencode/src/question/index.ts:64-153`). The question shape is structured, not free text: `{question, header, options:[{label,description}], multiple?, custom?}` (`packages/schema/src/v1/question.ts:15-31`), and the tool description tells the model to put a recommended option first and not to add catch-all options because "type your own" is automatic (`packages/opencode/src/tool/question.txt`). The TUI renders one tab per question plus a confirm tab, with multi-select and a custom-answer editor (`packages/tui/src/routes/session/question.tsx:17-60`). Epsilon has an approval channel but no model-initiated question tool; land it as an `epsilon-tools` tool backed by a new request/response type in `epsilon-contracts`, with answers surfaced over the existing event bus so TUI, server, and rpc frontends can each answer it.

### 11. Tool-call repair and the `invalid` tool
Before a tool call is dispatched, `experimental_repairToolCall` lower-cases the requested name and, if that matches a real tool, silently repairs the call; otherwise it rewrites the call into the `invalid` tool with `{tool, error}` as input (`packages/opencode/src/session/llm.ts:296-312`). The `invalid` tool's whole job is to return `The arguments provided to the tool are invalid: …` as a normal tool result (`packages/opencode/src/tool/invalid.ts:9-20`), and it is registered but excluded from `activeTools` so the model never sees it as callable (`registry.ts:231-233`, `session/llm.ts:317`). Schema failures get their own typed error whose message ends "Please rewrite the input so it satisfies the expected schema" (`packages/opencode/src/tool/tool.ts:24-34`). Epsilon's loop currently treats an unknown tool name or bad arguments as a tool failure; routing it into a synthetic corrective result would keep the turn alive. This is the cheapest row in the table: one branch in `epsilon-core/src/exec.rs` plus a hidden tool entry in `epsilon-tools/src/lib.rs`.

### 12. Pinned ripgrep
When a system `rg` is missing or unsuitable, opencode downloads its own pinned build (VERSION `15.1.0`, per-platform URL incl. musl/msvc) into the global bin directory and extracts it with `tar` or PowerShell `Expand-Archive` (`packages/core/src/ripgrep/binary.ts:14-27`, `:105`). grep and glob then run through that one engine at a limit of 100 results, with truncation noted in the output (`packages/opencode/src/tool/grep.ts:63-68`, `packages/opencode/src/tool/glob.ts:49-51`). Epsilon's `grep`/`glob`/`find` walk the tree with a regex crate and a `.gitignore` approximation (`crates/epsilon-tools/src/search.rs:1-7`, `crates/epsilon-tools/src/find.rs:1-5`), so ignore semantics, symlink handling, and binary-file skipping can silently differ from what the user's tools see. Port the *semantics*: either shell out to `rg` when present (preferred, exact) or tighten the walker to gitignore-exact behaviour with tests contrasting the two. Do not port runtime binary downloads; bundling or requiring `rg` is the honest variant.

### 13. Subagent depth, derived permissions, background promotion
Before spawning, the task tool walks `parentID` links and refuses past `subagent_depth` (default 1; config at `packages/core/src/v1/config/config.ts:84`), with an error that names the config key (`packages/opencode/src/tool/task.ts:104-117`). Child sessions get a derived ruleset: parent `external_directory` rules and all parent denies are inherited, and the child's own ruleset decides its capabilities — with `todowrite` and `task` denied unless the child agent explicitly permits them (`packages/opencode/src/agent/subagent-permissions.ts:14-27`, applied at `task.ts:139-155`). A running foreground task can also be promoted to a background job: `background.start({onPromote})` fires when the parent moves on, and the result is injected into the parent session as a synthetic `<task state="completed">` message (`task.ts:256-318`). Epsilon has background+resume but no depth cap, no child-permission derivation, and no promote path; all three are additive to `epsilon-tools/src/task.rs` plus a `subagent_depth` entry in `epsilon-core/src/config.rs`.

### 14. Model-family system prompts
A single `SystemPrompt.provider(model)` switch picks one of nine embedded base prompts by model/provider id — meta/muse (with `{{MODEL_NAME}}` substituted), beast for gpt-4/o1/o3, codex for gpt\*codex, gpt, gemini, claude, trinity, kimi, default (`packages/opencode/src/session/system.ts:27-49`, files in `packages/opencode/src/session/prompt/`). Alongside it, the system context includes an environment block (working dir, worktree, is-git, platform, date), verbose skill listing (names + descriptions only), and MCP server instructions filtered per agent permission (`system.ts:67-135`). The shell tool's own description is regenerated per resolved shell (bash/pwsh/cmd/powershell) with platform-specific chaining and quoting guidance (`packages/opencode/src/tool/shell/prompt.ts:221-291`). Epsilon emits one embedded contract plus generic guidelines for every model (`crates/epsilon-core/src/prompt.rs:62-81`) and a single bash description (`crates/epsilon-tools/src/descriptions/bash.txt`). Port per-model-family preamble variants and shell-specific tool text, keeping Epsilon's tier/hash discipline so cache tests still pass.

### 15. Tool-output spill policy
`Truncate.output(text, options, agent)` compares line and byte counts against config-resolved limits (`tool_output.max_lines` default 2000, `max_bytes` default 51200, `packages/core/src/v1/config/config.ts:136-148`), keeps a head or tail window, writes the full text to a shared flat `tool-output` directory, and returns a preview that names the file plus a hint (`packages/opencode/src/tool/truncate.ts:85-141`). The hint is agent-aware: if the agent can call the task tool it says to delegate inspection of the spilled file to an explore subagent rather than reading it into context (`:27-30`, `:129-131`). A cleanup loop deletes `tool_*` files older than 7 days on an hourly schedule (`:12`, `:53-66`). The bash tool streams into the same store, keeping only the last `maxBytes * 2` in memory, and appends a `<shell_metadata>` block for timeout/abort notes (`packages/opencode/src/tool/shell.ts:428-595`). Epsilon spills via `ToolContext.spill_dir` (`crates/epsilon-contracts/src/tool.rs:282`) but has no retention sweep, no direction option, and no delegation hint — all three are small deltas in `epsilon-tools/src/util.rs`.

### 16. Compaction tail and prune policy
Beyond Epsilon's tail clamp, opencode keeps `PRUNE_PROTECT = 40_000` tokens of recent tool output, prunes only if the reclaimed amount exceeds `PRUNE_MINIMUM = 20_000`, never prunes a `skill` result, stops at the previous summary boundary, requires at least two turns of history, and marks pruned parts with `time.compacted` so projection renders `[Old tool result content cleared]` (`packages/opencode/src/session/compaction.ts:28-31`, `:273-317`). Tail selection walks turns backwards, estimating lazily so cost tracks the retained tail, and when a turn does not fit it can *split* the turn at a safe message boundary so the tail starts mid-turn instead of dropping the whole exchange (`:223-268`, `:150-162`). `tail_turns` (config, default unlimited) caps retention independently of the token budget (`packages/core/src/v1/config/config.ts:157-159`). Epsilon's `crates/epsilon-core/src/compact.rs` prunes tool results and clamps tail tokens to 2k–15k with no turn alignment. Port the floor/ceiling thresholds, the protected-tool list, and turn-aligned tail selection; the mid-turn split is the most delicate part and should land with transcript fixtures.

### 17. TUI diff viewer and status panels
The diff viewer parses the session patch into files and hunks, tracks a file tree with expand/collapse state, supports split vs unified rendering (auto by terminal width or config `diff_style`), hunk-by-hunk and file-by-file navigation, single-patch mode, and a per-file "reviewed" set — all driven by a dedicated keymap block (`packages/tui/src/feature-plugins/system/diff-viewer.tsx:114-174`, `packages/tui/src/feature-plugins/system/diff-viewer-file-tree.tsx`, `packages/tui/src/config/keybind.ts:60-75`). `util/revert-diff.ts:1-16` derives per-file addition/deletion counts from a patch for the revert banner. Sidebar panels show context usage (tokens, percent of model context, session cost), todos (collapsed when >2 items or all complete), connected LSP servers, and MCP status (`packages/tui/src/feature-plugins/sidebar/context.tsx:20-55`, `sidebar/todo.tsx:1-40`, `sidebar/lsp.tsx:1-45`, `routes/session/footer.tsx:20-40`). Epsilon's ratatui TUI has no diff view (grep clean). Land the panels first (todo/context/LSP are cheap and read existing state), then a unified-only diff viewer; the file tree and hunk navigation can follow.

### 18. Skill loading details
`Skill.require(name)` is permission-checked with the skill name as the pattern, so a project can allow or deny individual skills (`packages/opencode/src/tool/skill.ts:34-39`). The returned body is wrapped in `<skill_content name=…>` with a note that relative paths resolve against the skill's base directory, plus a sampled list of the other files in that directory (`:41-66`) — which is how bundled `scripts/` and `references/` get discovered. The prompt-side catalog lists names and descriptions only, deliberately, while the tool description stays terse (`packages/opencode/src/session/system.ts:105-117`). Epsilon reads the SKILL.md body and strips frontmatter (`crates/epsilon-core/src/skills.rs:25-42`) with no auxiliary file listing and no per-skill permission gate. Port both small pieces: a `skill` capability in the ruleset engine (`crates/epsilon-safety/src/engine.rs`) and a bounded directory listing appended to the loaded body.

### 19. Code-mode `execute` tool
Instead of exposing every MCP tool as a separate schema, opencode exposes one `execute` tool whose description is generated from the MCP catalog as a namespaced tool tree via `CodeMode.instructions()` (`packages/opencode/src/tool/code-mode.ts:58-65`), and the tool description is only advertised when that catalog is non-empty (`packages/opencode/src/tool/registry.ts:280-289`, `:305-308`). Inside, each child call goes through the parent's permission `ask` with the MCP tool key as the permission name, plus `tool.execute.before/after` plugin hooks, and per-call progress is published to tool metadata as `{tool,status,input}` entries (`code-mode.ts:134-186`, `:214-260`). Results are projected from MCP content blocks to text/structured values with attachments extracted separately (`:75-116`), and the whole run races the abort signal. Epsilon has an MCP client but no orchestration layer; porting means adding a confined script runtime (Lua/WASM/Rhai) behind a feature flag and a catalog-description generator. Highest effort and highest risk in this list — worth a spike before a commitment.

### 20. Context epochs and mid-conversation system messages
System context is modelled as typed sources with a stable namespaced key, a codec, a loader that can return `unavailable`, and pure baseline/update/removal renderers (`packages/core/src/system-context/index.ts:16-40`); built-ins cover environment and date (`packages/core/src/system-context/builtins.ts:26`, `:34`). At session start the composed context is observed once and persisted as an immutable **baseline** with a snapshot of each source value; on each subsequent turn `prepare()` re-observes, and if any source changed it publishes `SessionEvent.ContextUpdated` carrying the rendered update text while advancing the stored snapshot atomically — otherwise the stored baseline is reused verbatim (`packages/core/src/session/context-epoch.ts:40-78`). Compaction starts a new epoch and folds the current context into a fresh baseline (`:59-70`). The runner then sends `system: [agent.system, baseline]` and appends the durable update messages chronologically (`packages/core/src/session/runner/llm.ts:183-215`). Epsilon rebuilds a volatile tier per turn (`crates/epsilon-core/src/prompt.rs:111-116`); the epoch model would let the date/instruction/skill changes ride as messages instead of touching the cached prefix. Note: this is wired in the V2 core runner, not the legacy loop — treat it as a design to adapt, not code to translate.

## Deliberately do not port

- The Effect/TypeScript runtime, `InstanceState`/`LayerNode` service graph, and `@opencode-ai/*` package split: Epsilon's compile-time-dependency Rust workspace already enforces the same layering more cheaply.
- Drizzle/SQLite session storage and the `SessionStore`/`LocationServiceMap` placement model: Epsilon's JSONL tree sessions with cross-process leases and crash repair are stronger for its single-binary, multi-frontend story.
- The generated client/SDK stack (`packages/client`, `protocol`, `httpapi-codegen`, `sdk-next`, `packages/app`, `web`, `desktop`, `session-ui`, `console`, `enterprise`, `slack`, `stats`): product surfaces, not harness mechanics.
- In-process Bun plugins: Epsilon's process-isolated extension host is a deliberate safety property; port only the *hook list* shape.
- `experimental.chat.system.transform` and `experimental.chat.messages.transform`: arbitrary prompt rewriting fights Epsilon's byte-stable tiers (opencode itself flags the V2 equivalent as an open ambiguity, `CONTEXT.md:223-225`).
- Runtime downloads/installs of toolchains and language servers (`lsp/server.ts:206-208`, `:372`, `:756`, `ripgrep/binary.ts:105`): network + build side effects at first use are not acceptable defaults for a harness that must work offline.
- opencode's TUI stack (opentui/Solid) and its plugin-route architecture: Epsilon's ratatui frontend is the base; only interaction patterns transfer.
- The full per-model `provider/transform.ts` quirk table (66 KB of provider-specific message surgery): port cache markers and leave the rest until a concrete provider needs it.
- opencode's SQL-driven `SessionV2` runner with durable prompt inbox rows: Epsilon's steering/follow-up queues plus two-level loop already cover the semantics without a database.
- Their `subagent_depth` default of 1 combined with permission-derived child denies is worth porting (row 13); the surrounding agent/service config sprawl is not.
